# domain-adaptable-skill

Cofa Probe 환경(크래프톤의 AI 실무 역량 평가 플랫폼)에서 열리는 해커톤을 위해, **Claude Code에 업로드해서 쓰는 개인 하네스**입니다.
어떤 도메인의 과제가 나와도(웹 서비스, 데이터 파이프라인, EDA 툴 자동화, 사내 자동화 플랫폼) 같은 순서로 일할 수 있게 만들었습니다.

## 30초 설명
Cofa Probe는 결과물만 보지 않습니다. 6시간 동안 **AI와 어떻게 일했는지**(어떤 질문을 했나, 어떻게 쪼개 위임했나, 어떻게 검증했나, AI의 과잉 설계를 통제했나, 토큰을 얼마나 썼나)를 20여 개 평가 에이전트가 기록하고 채점합니다.
이 하네스는 그 평가 방식에 맞는 일하는 순서를 **슬래시 명령 5개와 선택 명령 1개(`/grill`)**로 만들고, 과정에서 생기는 지식과 결정을 **`docs/` 폴더의 파일**로 남깁니다. 파일이 남으니 세션을 비워도 안전하고, 토큰이 적게 듭니다. 결정 기록은 명령이 알아서 하고, 명령 하나의 답은 15줄 이내로 짧습니다. `/grill`은 도메인 지식을 내 말로 다지고, 끝에 요약과 퀴즈로 내가 설명할 수 있는지 확인합니다. 퀴즈는 커밋·푸시를 막지 않습니다.

## 10분 빠른 시작 (당일)
1. **미리**: `scripts/pack.sh`로 `dist/harness.zip`을 만들어 챙기고, `docs/03-cheatsheet.md`를 인쇄합니다.
2. **시작 직후 확인 (3분)**: 터미널의 AI 도구(`claude --version`, 없으면 `codex`), 제한 시간, 파일 업로드 가능 여부, 인터넷. 전체 목록은 `docs/01-cofa-probe.md` 8절. Codex뿐이거나 업로드가 안 되면 아래 "자주 묻는 질문"을 따릅니다.
3. **설치**: 과제 프로젝트 루트에서 zip을 풉니다. `unzip -n harness.zip` (로컬 테스트는 `scripts/install.sh <프로젝트 경로>`)
4. **시작**: `claude`를 실행하고 제한 시간을 붙여 `/kickoff 4h`처럼 입력합니다(2차 예선은 4시간, 생략하면 6시간으로 계산). 이후 할 일은 각 명령이 마지막 줄에 알려줍니다.

## 6개 명령 (`/grill`은 선택)
| 명령 | 언제 | 하는 일 | 남기는 것 |
|---|---|---|---|
| `/kickoff [경로] [4h]` | 시작 직후 1회 | 과제 지시문을 내 말로 재정의, 모르는 것 6범주, 시간표 | `docs/` 뼈대, SPEC 1·7절, TASKS 시간표 |
| `/interview [답변]` | 탐색 단계, 반복 | 처음엔 질문 3~5개(바텀업 사다리). 페르소나의 답을 붙이면 사실·용어·제약으로 나눠 기록하고 다음 질문까지 | `domain/*.md`, `GLOSSARY.md`, SPEC 3·5절 |
| `/grill [주제\|quiz]` | 인터뷰 뒤 `/spec` 전(선택). 마감 전이나 제출 뒤에는 `quiz` | 용어·단위·경계 사례·문서와 샘플의 모순을 한 번에 하나씩 추천 답과 함께 묻고, 답을 바로 기록. 모르면 페르소나에게 넘긴다. 끝에 쉬운 말 요약과 4문항 퀴즈 | 기존 `GLOSSARY.md`·`domain/`·`DECISIONS.md`만 (퀴즈는 파일 없음) |
| `/spec` | 인터뷰 후 (새 요구가 생기면 다시) | P0 3개 이하·비목표 확정, 입출력을 샘플 값으로, 검증 명령이 붙은 슬라이스. 모듈이 여럿일 때만 CONTRACT와 모듈 지침 | `SPEC.md`, `fixtures/`, `TASKS.md`, 커밋 |
| `/delegate <ID>` | 슬라이스마다 | 브리프 → 승인 → 서브에이전트 위임 → 루트에서 재검증·회귀 확인 → 과잉 설계 제거 제안 → 보드 갱신 → 커밋 | `docs/briefs/`, 구현, 커밋 |
| `/wrapup [check\|retro]` | 마감 60분 / 30분 전 | 통합 검증·화면 확인·저장소 전체 정리·실행 README / 복기 문서 | `RETRO.md` |

모든 명령은 **사람이 호출**합니다. 모델이 알아서 꺼내 쓰지 않도록 설정(`disable-model-invocation: true`)했기 때문에, 호출하기 전까지 토큰을 전혀 쓰지 않고, "내가 단계를 지휘했다"는 로그가 남습니다. 처음에는 명령이 9개였는데 직접 해 보니 너무 복잡해서 5개로 합쳤습니다(`docs/04-design-notes.md` 8절). 그 뒤 도메인 지식을 다지고 퀴즈로 확인하는 선택 명령 `/grill`을 더했습니다(9절).

## 세 가지 설계 원칙
### 1. 도메인 지식을 쌓는 구조 (grill-with-docs 방식)
grill-with-docs는 계획을 집요하게 인터뷰하면서 합의된 용어를 `GLOSSARY.md`에, 결정을 ADR에 바로 적는 스킬입니다. 여기서는 인터뷰 상대가 사용자가 아니라 **페르소나 에이전트**이므로, `/interview`가 질문을 만들고, 답을 붙여 실행하면 소화해서 `docs/domain/<주제>.md`, `GLOSSARY.md`, `SPEC.md`에 나눠 적은 뒤 다음 질문을 냅니다. `domain/README.md` 인덱스만 읽어도 무엇을 아는지 보이고, 모듈은 필요한 파일 하나만 엽니다. 결정은 명령이 생길 때마다 `DECISIONS.md` 한 파일에 D-NNN으로 쌓습니다.

`/grill`은 grill-with-docs를 더 그대로 따릅니다. 이번에는 사람에게 직접 묻습니다. 문서의 빈틈(GLOSSARY와 다르게 쓰는 말, 단위·경계, 경계에 걸리는 사례, 문서와 샘플의 모순)을 한 번에 하나씩 추천 답과 함께 묻고, 답은 기존 문서 한 곳에 바로 적습니다. 새 파일은 만들지 않습니다. 끝에는 blindspot의 보고서·퀴즈처럼 쉬운 말 요약과 4문항 퀴즈를 터미널에 냅니다. 퀴즈는 복습용이라 결과를 남기지 않고, 커밋·머지·푸시를 막지 않습니다.

### 2. 과잉 설계 방어 (ponytail 방식)
ponytail은 "게으른 시니어 개발자" 규칙입니다. 쓰기 전에 사다리(필요한가 → 이미 있나 → 표준 라이브러리 → 설치된 의존성 → 한 줄 → 최소 구현)를 내려가고, 보안·입력 검증·데이터 보호는 절대 자르지 않으며, 답변 끝에 뺀 것과 리스크를 적습니다. 이 규칙을 `CLAUDE.md`에 12줄로 **항상 켜 두고**(스킬은 모델이 자동으로 꺼내 쓰지 않는 경우가 많아서), 감사는 `/delegate`(슬라이스마다 diff)와 `/wrapup`(제출 전 저장소 전체)이 합니다. Cofa Probe에 맞춰 **쳐낸 것을 `DECISIONS.md`에 자동으로 기록**합니다. 그 기록이 인지 점수와 Q&A 답변의 근거가 됩니다.

### 3. 토큰을 아끼는 구조
| 무엇 | 언제 로드되나 | 크기 (근사) |
|---|---|---|
| 루트 `CLAUDE.md` | 항상 | 51줄, 약 1,100 토큰 |
| 스킬 설명 6개 | 항상이지만 사용자 호출 전용이라 | 0 |
| 스킬 본문 1개 | `/명령` 입력 때만 | 840~1,310 토큰 |
| 참고 파일 4개 | 본문이 가리킬 때만 | 300~630 토큰 |
| 모듈 `CLAUDE.md` | 모듈이 여럿일 때, 그 폴더를 만질 때만 | 40줄 이하 |

세션 시작 고정 비용은 약 1,100 토큰입니다. 상태는 모두 `docs/`에 있으므로 슬라이스가 끝날 때마다 `/clear`로 비우고, 구현은 새 컨텍스트에서 시작하는 서브에이전트가 맡습니다. `scripts/check.sh`가 이 예산을 지키는지 검사합니다.

- 반도체 현장 사전 지식 `harness/.claude/skills/kickoff/templates/docs/domain/primer.md`가 들어 있습니다(SK하이닉스 본선 대비). 설치와 패키징에 자동으로 포함되고, `/interview`가 질문 재료로만 읽습니다. 다른 도메인 대회라면 지우거나 바꾸세요.
- `scripts/check.sh`로 하네스 상태를 확인하고 `scripts/pack.sh`로 zip을 만듭니다.

## 자주 묻는 질문
**웹 프로젝트가 아니어도 되나요?** 됩니다. 하네스 어디에도 frontend/backend 가정이 없습니다. 계약은 API·CLI·파일 포맷·함수·상태 전이 중 맞는 것으로 적습니다. 예시는 `harness/.claude/skills/spec/contract-examples.md`에 있습니다.

**하네스를 못 올리면?** 치트시트 맨 아래의 6줄짜리 최소 CLAUDE.md를 손으로 입력하고 `docs/` 파일 3개(SPEC·TASKS·DECISIONS) 이름만 지키면 같은 흐름으로 일할 수 있습니다.

**명령이 안 보이면?** Claude Code 버전이 오래된 경우 `.claude/skills/<name>/SKILL.md`를 `.claude/commands/<name>.md`로 복사하면 같은 형식으로 동작합니다.

**Claude Code 대신 Codex만 있으면?** 프로젝트 루트에서 `cp CLAUDE.md AGENTS.md && mkdir -p .agents && cp -r .claude/skills .agents/skills`를 실행하고, 명령을 `/kickoff` 대신 `$kickoff`처럼 부릅니다. Codex CLI 0.164.0에서 스킬이 보이고 `$kickoff`가 절차대로 동작하는 것을 확인했습니다(명령이 9개였던 이전 버전으로 확인). 서브에이전트 위임(`$delegate`)은 확인하지 못했습니다. 코파톤 과제는 Codex 기반이었다는 보도가 있습니다(`docs/01-cofa-probe.md` 8절).

**왜 모듈을 많이 안 나누나요?** 나누는 것 자체가 과잉 설계일 수 있습니다. 기본은 1개이고, 검증 방법이 다르거나 병렬로 만들 가치가 있을 때만 나눕니다. 모듈이 1개면 계약(입출력 샘플)은 `SPEC.md` 8절에 두고 `CONTRACT.md`와 모듈 지침은 만들지 않습니다.

**git에 올려도 되나요?** `harness/`는 그대로 커밋해도 됩니다. `dist/`는 `.gitignore`에 있습니다.
