# 데이터·환경·제약

## 입력 데이터 (출처, 형식, 규모, 갱신 주기)
- 입력은 매일 밤 회귀 테스트의 로그 파일. 실패 여부는 `UVM_ERROR`/`UVM_FATAL` 문자열로 판단한다. (인터뷰 1회차) → 끝 요약 줄을 뺀 실제 에러 줄 기준(D-001), 끊긴 로그도 실패(인터뷰 3회차).
- LSF 시간 제한은 4시간. 넘으면 로그가 중간에 끊긴다. (인터뷰 3회차)
- 회귀는 보통 아침 7시쯤 끝난다. 8시에 아직 도는 실행은 거의 본 적 없지만 장담은 못 한다 → 아직 도는 로그와 끊긴 로그는 끝 줄만으로 구별되지 않는다. (인터뷰 4회차)
- 위치: `/proj/soc/regress/<날짜>/`. 날짜 = 회귀를 시작한 밤의 날짜(아침 정리 날짜보다 하루 앞). 날짜 표기 형식, 하위 폴더 유무는 미확인. (인터뷰 2회차)
- 파일 이름: `<테스트이름>__s<seed>.log`. 테스트 이름·seed는 여기서 얻는다. (인터뷰 2회차)
- 실패마다 필요한 값: 테스트 이름, seed, 첫 번째 에러 줄. (인터뷰 1회차)
- 규모: 하룻밤 약 300개 실행(테스트 약 60종 × seed 약 5개). 실패가 많은 날은 40개가 넘는다. (인터뷰 1·2회차)
- 에러 줄 안에 `[SCB]` 같은 태그와 주소·값이 들어 있다. 실제 줄 예시는 아직 못 봄. (인터뷰 2회차)
- 어제 결과는 메신저에 올린 텍스트 글로만 남는다. 다른 저장 위치 없음. (인터뷰 2회차) 어제 날짜의 로그 폴더가 다음 날에도 남아 있는지는 미확인.
- 지난 결과를 도구가 어떻게 남길지는 만드는 쪽에 맡겼다. 조건 두 가지: 휴가 대리 동료도 **똑같이** 쓸 수 있을 것, 비교 기준이 **실제로 마지막에 올린 결과와 어긋나지 않을 것**. (인터뷰 4회차)
- 비교 기준은 "어제"가 아니라 마지막으로 올린 글(월요일이면 보통 금요일 글). 주말 등 그 사이 밤의 결과는 비교에 안 들어간다. (인터뷰 3회차)

## 실행 환경 (런타임, 네트워크, 권한, 기존 시스템)
- 사내 서버, 인터넷 안 됨. (인터뷰 2회차)
- Python 3.6 고정(서버 관리팀 관리, 버전 못 올림), pip 설치 불가. bash·grep·awk 사용 가능. (인터뷰 2회차)
- 지금 쓰는 도구는 grep과 엑셀뿐, 쓰는 스크립트 없음. (인터뷰 2회차)
- 결과는 팀 메신저 채널에 텍스트로 붙여 넣는다. (인터뷰 1회차)
- 메신저 한 메시지는 4000자를 넘기면 안 된다(담당자 말). 원인이 많은 날 에러 줄 원문을 다 붙이면 넘길 수 있어 나눠 올려야 한다. (인터뷰 5회차)
  - 4000자는 메신저가 막는 정해진 한도다. 넘으면 올라가지 않는다. "읽기 편한 길이" 같은 별도 기준은 없다 → 길이 기준은 4000자 하나. (인터뷰 6회차)
  - 지금 게시 글은 4000자를 넘겨 본 기억이 거의 없다. 넘으면 두 번에 나눠 올리면 된다고 보지만, 어디서 끊을지는 해 본 적이 없다 → 끊는 위치는 만드는 쪽이 정한다. (인터뷰 6회차)
  - 참고: samples 출력의 묶음 한 줄은 140~175자 → 한 메시지에 대략 20묶음 남짓 (루트 측정)

## 읽기/쓰기 특성 (동시 사용자, 쓰기 충돌 가능성)
- 하루 한 번, 한 사람만 정리한다(휴가 시 대리 1명). 동시 쓰기 없음. (인터뷰 1회차)

## 예외·엣지 케이스
- 휴가 대리자가 실행해도 같은 기준으로 비교돼야 한다. (인터뷰 1회차)
- 같은 테스트가 seed마다 다른 에러로 실패할 수 있다. (인터뷰 2회차)
- 같은 테스트·같은 태그인데 원인이 다른 실패가 있다(DMA 사례). 파일 이름과 태그만 보고 비교하면 놓친다. (인터뷰 2회차, D-002로 정정)

## 금지·주의 (보안, 개인정보, 규정)
- 팀 위키 "알려진 실패" 표는 비교 기준으로 쓰지 않는다(신뢰도 낮음). (인터뷰 1회차)
- 외부 패키지·인터넷 의존 금지(설치 불가). (인터뷰 2회차)
