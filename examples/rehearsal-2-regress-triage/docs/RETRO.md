# RETRO

## 1. 무엇을 만들었나 (3문장)
SoC 검증팀 담당자가 매일 아침 `python3 regsum.py <회귀 날짜 폴더> <보관 폴더>` 한 번으로 팀 채널에 붙여 넣을 회귀 정리 글을 얻는 CLI 하나(`regsum.py`, 212줄, Python 3.6 표준 라이브러리만)를 만들었다.
글은 **끊긴 로그 → 새로 생긴 실패 → 계속 남은 실패** 순서이고, 실패 묶음당 한 줄(테스트 이름·seed·첫 에러 줄)이며, 직전 보관 파일과 비교해 1순위인 "새로 생긴 실패를 놓치지 않기"를 지킨다.
실행마다 보관 파일(`<날짜>.tsv`)을 남겨 다음 날 비교 기준이 되고, 글이 4000바이트를 넘는 날만 줄 경계에서 메시지 여러 개로 나눈다.

## 2. 사용자와 핵심 흐름 (GLOSSARY 용어로)
- 사용자: 검증팀 담당자 1명(휴가 때 대리자). 아침 8시쯤 사내 서버 터미널에서 한 번 돌리고 9시 스탠드업 전에 붙여 넣는다. 읽는 사람은 팀원과 설계팀(새로 생긴 실패 통보).
- 흐름:
  1. 회귀 날짜 폴더의 로그마다 **실패 로그**(끝 요약 줄 말고 실제 에러 줄이 있는 로그)와 **끊긴 로그**(`UVM Report Summary`도 `$finish`도 없는 로그)를 가려 **실패 실행**을 찾는다.
  2. 실패 실행의 **첫 에러 줄**에서 숫자(16진 먼저, 10진)를 `#`로 바꿔 **묶음 기준 줄**을 만들고, 같은 테스트 이름 + 같은 묶음 기준 줄이면 한 **실패 묶음**으로 묶는다.
  3. **비교 기준**(이번 **회귀 날짜**보다 앞선 가장 최근 **보관 파일**)에 그 묶음이 없으면 **새로 생긴 실패**, 있으면 **계속 남은 실패**(seed 수가 바뀌면 `1개에서 2개로`).
  4. 게시용 글을 표준출력에, 이번 묶음 목록을 보관 파일에 쓴다. **메시지 한도**를 넘으면 **나눠 올리기**.

## 3. 구조 (모듈 표 + 왜 이렇게 나눴나 / 안 나눴나)
| 모듈(파일) | 아키타입 | 입력 | 출력 |
|---|---|---|---|
| `regsum.py` (하나) | CLI, Python 3.6 표준 라이브러리만 | 회귀 날짜 폴더, 보관 폴더 | 표준출력 = 게시용 글, 보관 폴더에 `<회귀 날짜>.tsv` |

- 안에서는 함수로만 나눴다: 규칙(`is_error_line`·`is_truncated`·`failure_key`) → 수집(`collect`) → 비교(`pick_baseline`·`read_history`) → 글(`render`·`split_messages`·`_pack`) → `main`(오류 검사 → 보관 → 출력).
- **안 나눈 이유**: 검증 방법이 "샘플 → 기대 출력 diff" 하나뿐이고, 병렬로 맡길 만큼 크지 않으며, 서버에 파일 하나만 두면 되는 게 설치 제약(pip 불가)에 맞다. 진짜 경계는 모듈 사이가 아니라 **어제 실행 ↔ 오늘 실행**(보관 TSV)과 **도구 ↔ 사람**(CLI·글 모양)이라 그 둘을 CONTRACT C·D로 고정했다.
- 구현은 슬라이스 S0(뼈대) → S1(찾기·묶기) → S2(비교) → S3(오류 경로) → S4(나눠 올리기)로 서브에이전트에 브리프(`docs/briefs/`)로 위임하고, 루트가 매번 `fixtures/check.sh`로 검증했다.

## 4. SPEC 대비 (P0 완료·미완료, P1, 비목표로 뺀 것과 이유)
| ID | 우선순위 | 상태 | 확인 |
|---|---|---|---|
| F1 실패 실행 찾기 | P0 | 완료 | check.sh ① |
| F2 실패 묶음 | P0 | 완료 | ①, `fixtures/keys.tsv` 단위 테스트 |
| F3 비교·게시 글·보관 | P0 | 완료 | ①②③④ + 손 확인 오류 4행 |
| F7 나눠 올리기 | P1 | 완료 | ⑤, 로그 300개 합성 폴더에서 메시지 10개 모두 4000바이트 이하 |

- 비목표로 뺀 것과 이유
  - F5 사라진 실패, F6 사이 밤 실패: 담당자가 정해 둔 방식이 없고 4회차에 "이번엔 빼도 괜찮다".
  - 자동 게시·설계팀 통보·메일: 지금도 사람이 붙여 넣는다(workflow 5~6단계).
  - 위키 "알려진 실패" 연동: 신뢰도가 낮고 constraints.md 금지.
  - 옵션 플래그·설정 파일(기준 날짜 수동 지정, 한도 지정 등): 사용자 1명, 하루 1회. 대리자도 "같은 명령 = 같은 결과"여야 해서 옵션이 오히려 위험하다.
  - 잠금·병렬·캐시·재시도: 실행자 1명, 300개 로그가 0.03초.

## 5. 핵심 결정 (5개 이내: 선택·대안·이유 — DECISIONS 요약)
1. **D-001 실패 로그 정의**: 끝 요약 줄을 뺀 실제 에러 줄 기준. 단어 grep은 모든 로그 끝의 `UVM_ERROR :    0` 때문에 통과 로그까지 걸린다.
2. **D-002·D-004 같은 실패 = 같은 테스트 + 숫자를 `#`로 바꾼 첫 에러 줄**: 16진을 먼저 지운다(안 그러면 `0x0badf00d`가 `0xbadfd`로 남아 s202·s203이 갈라진다). 소스 줄 번호까지 지운다(담당자 기준 그대로, 코드만 고쳐도 매일 새 실패가 뜨는 걸 막는다). 다른 테스트끼리는 안 묶는다(덜 묶는 쪽 = 놓치지 않는 쪽).
3. **D-003 비교 기준 = 도구가 남긴 보관 파일 중 직전 날짜**: 채널 글을 다시 붙여 넣어 파싱하는 대안은 단계가 늘고 사람이 고친 글에 깨진다. 첫 줄에 비교 기준 날짜를 보여 어긋나면 사람이 바로 안다.
4. **D-005 보관 파일 = TSV, 깨지면 종료코드 2**: 게시 글 역파싱(`1개에서 2개로` 때문에 깨지기 쉬움)과 JSON(grep·awk로 보기 불편) 대신 TSV. 깨진 파일을 조용히 넘기면 모든 실패가 "새로 생김"으로 뜨니 멈춘다.
5. **D-007 나눠 올리기 = P1, UTF-8 바이트로 세고 줄 경계에서 꽉 채움, `(이어서)` 칸 제목 반복**: 메신저가 글자로 세든 바이트로 세든 안전하다. 칸 제목 없이 이어 붙이면 둘째 메시지의 새로 생긴 실패를 계속 남은 실패로 읽을 위험(1순위 위험)이 있다.

## 6. 거절하거나 축소한 AI 제안 (목록과 이유)
- **argparse·logging·클래스 계층·`csv` 모듈**: 브리프에서 처음부터 금지. 인자 2개, 출력 2개라 `sys.argv`와 `str.split("\t")`로 충분하다.
- **문서 문자열의 슬라이스 꼬리표 `(S1: 비교 없음)`**(D-006): SPEC 근거가 없고 슬라이스마다 낡는다. 커밋 메시지가 그 역할을 한다 → 제거.
- **`render`의 `kept_groups` 지금 삭제**(D-006): 다음 슬라이스 S2에서 바로 다시 넣어야 해서 거절 → S2에서 실제로 쓰임.
- **`tempfile.mkstemp`, 회귀 날짜 달력 검사, 보관 폴더 먼저 만들기**(D-008): 실행자 1명이라 고정 이름 `.tmp`면 충분하고, `2026-02-30` 같은 폴더는 사람이 만들지 않으며, 실패한 실행이 빈 폴더를 남기면 대리자가 헷갈린다.
- **`split_messages` 다시 나누기 루프 줄이기, `failure_key`의 탭→공백 제거**(D-009, /lean): 둘 다 정확성 코드라 유지. `[k/N]` 자릿수가 바뀌면 4000바이트를 넘을 수 있고, 탭이 남으면 TSV가 깨진다.
- **F7을 P0로**(D-007): P0 3개 상한, 드물고 줄 단위라 손으로도 나눌 수 있어 P1로 축소.

## 8. 시간이 더 있다면 (우선순위 3개)
1. **실제 서버의 Python 3.6과 실제 로그 300개에서 한 번 돌려 보기.** 여기서는 3.10과 합성 300개 폴더로만 확인했다. 3.7+ 문법은 쓰지 않았지만 3.6 실행 확인은 못 했다.
2. **SPEC 7 열린 질문 확인 인터뷰**: 공유 보관 폴더 경로, 게시 전에 글을 손으로 고치는지, 다른 테스트끼리 묶는지, 나눠 올리기 모양(`2026-10-26_split.txt`)이 붙여 넣기 편한지. D-004·D-005·D-007은 아직 "사람 확인 대기"다.
3. **F5 사라진 실패 표시**: 보관 파일에 이미 어제 묶음이 있어 집합 차이만 구하면 된다. 담당자가 정해 둔 방식이 생기면 칸 하나를 더한다.

## 9. 예상 질문 10개와 한 줄 답
1. **왜 파일 하나인가?** 검증이 diff 하나뿐이고 pip이 안 되는 서버에 그대로 두는 게 설치의 전부라서다. 진짜 경계(보관 TSV, CLI·글 모양)는 CONTRACT로 고정했다.
2. **`UVM_ERROR`로 grep하면 안 되나?** 모든 로그 끝 요약에 `UVM_ERROR :    0`이 있어 통과 로그까지 걸린다. 요약 줄 정규식을 빼고 센다(D-001).
3. **숫자를 다 지우면 다른 원인이 하나로 묶이지 않나?** 담당자 기준이 원래 "숫자를 뺀 같은 줄"이다. DMA 사례는 숫자가 아니라 뒤쪽 메시지가 달라서 기준 줄로 갈린다(check.sh ②). 애매하면 덜 묶는다.
4. **왜 16진수를 먼저 지우나?** 10진수만 지우면 `0x0badf00d`가 `0xbadfd`로 남아 같은 원인의 s202·s203이 갈라진다.
5. **비교 기준을 왜 채널 글이 아닌 보관 파일로?** 사람이 고친 글을 매일 파싱하는 건 깨지기 쉽다. 대신 첫 줄에 비교 기준 날짜를 보여 어긋남을 사람이 잡는다(D-003).
6. **보관 파일이 깨지면?** 종료코드 2로 멈추고 파일·줄 번호를 알려 준다. 조용히 넘기면 모든 실패가 "새로 생김"으로 뜬다. 쓰기는 `.tmp` → `os.replace`로 중간에 죽어도 어제 파일이 안전하다.
7. **4000을 왜 바이트로 세나?** 메신저가 세는 단위를 모른다. UTF-8 바이트 수는 글자 수보다 작지 않아 어느 쪽이든 안 넘는다(D-007).
8. **어떻게 검증했나?** CONTRACT 샘플 명령을 `fixtures/check.sh` ①~⑤로 만들어 기대 출력과 diff 0, 단위 테스트 19개, 오류 경로 4행 손 확인, `LANG=C`에서 출력 동일, 300개 합성 폴더에서 메시지 모두 4000바이트 이하.
9. **AI에 끌려가지 않은 근거는?** SPEC 비목표 목록과 브리프 금지 목록(argparse·클래스 등)을 먼저 적고, /lean에서 슬라이스 꼬리표를 지우고, 대안·기각 이유를 DECISIONS에 남겼다. 결정이 필요한 건 사람에게 하나씩 물었다(D-007 해석 (나) 등).
10. **토큰은 어떻게 아꼈나?** 맥락을 `docs/`에 두고 CLAUDE.md는 짧게 유지했다. 슬라이스마다 서브에이전트에 읽을 파일과 열지 말 파일을 정한 브리프만 줬고, 검증은 diff 한 줄로 해서 출력 전체를 읽지 않았다. 슬라이스가 끝나면 `/clear` 해도 안전했다.
