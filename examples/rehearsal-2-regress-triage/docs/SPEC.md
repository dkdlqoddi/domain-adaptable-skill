# SPEC — 요구사항 정의서

> 루트 세션만 수정. 인터뷰(`/interview`)로 확인된 내용만 적는다. 추측은 `(가정)` 표시.

## 1. 한 줄 목표
SoC 검증팀 담당자가 매일 아침 지난밤 회귀 결과를 팀 채널에 올릴 때, **새로 생긴 실패를 놓치지 않고** 붙여 넣을 글을 명령 하나로 얻게 한다. 1순위 = 새로 생긴 실패를 놓치지 않기, 2순위 = 10분 안에 끝내기 (success.md, 인터뷰 3회차)

## 2. 사용자와 상황
- 주 사용자: 검증팀 담당자 1명. 휴가 때만 옆자리 동료가 대리하고, 대리자도 **같은 명령으로 같은 결과**를 얻어야 한다 (persona.md, 인터뷰 1·4회차)
- 사용 상황: 매일 아침 8시쯤 한 번, 사내 서버 터미널. 9시 스탠드업 전에 채널에 올린다 (workflow.md, 인터뷰 1회차)
- 글을 읽는 사람: 팀원(스탠드업), 설계팀(새로 생긴 실패 통보) (persona.md)

### P0 세부 규칙 (판단 근거가 있는 것만)
- 실패 로그 = 끝 요약 줄(`UVM_ERROR :    0` 등)을 뺀 실제 에러 줄이 하나라도 있는 로그 (D-001)
- 끊긴 로그 = `UVM Report Summary` 줄도 `$finish` 줄도 없는 로그. 에러 줄이 있어도 끊긴 로그로 맨 위에 둔다 (가정: 덜 묶는 쪽, domain/README 추천). 8시에 아직 도는 실행도 끝 줄로는 구별이 안 되므로 같은 칸에 두고 칸 제목에 "또는 아직 실행 중"을 붙인다 (가정, 인터뷰 4회차 사실에서 도출)
- 묶음 기준 줄 = 첫 에러 줄에서 16진수(`0x…`)와 10진수를 모두 `#`로 바꾼 줄. 소스 줄 번호·시뮬 시간도 숫자이므로 같이 지운다 (D-004, 담당자 기준 "숫자를 뺀 같은 줄" 그대로)
- 다른 테스트끼리는 묶음 기준 줄이 같아도 다른 묶음 (D-004, 게시 예시가 테스트 단위)
- 비교 기준 = 이번 회귀 날짜보다 앞선 보관 결과 중 가장 최근 것. 출력 첫 줄에 비교 기준 날짜를 보인다 (D-003)
- 보관 결과가 하나도 없으면(첫 실행) 모든 실패 묶음을 새로 생긴 실패로 올린다 (가정: 덜 묶는 쪽)
- 계속 남은 실패의 실패 seed 수가 지난번과 다르면 `2개 중 1개에서 2개로`처럼 보인다. 줄어든 경우도 같은 모양 (가정)
- 묶음 한 줄에 보이는 첫 에러 줄은 seed가 가장 작은 실패 실행의 원문 그대로 (가정: 지금 글이 `테스트 이름, seed, 첫 에러 줄`이라 원문을 쓴다. lane 번호도 원문에 남아 참고가 된다)
- `UVM_ERROR`/`UVM_FATAL`은 구분하지 않는다. 원문에 등급이 보인다 (가정)

### F7 세부 규칙 (D-007, 모양은 `CONTRACT.md` C "나눠 올리기")
- 메시지 한도 = 4000. **UTF-8 바이트로 센다.** 바이트 수는 글자 수보다 작지 않으므로 메신저가 글자로 세든 바이트로 세든 넘지 않는다 (가정: 메신저가 세는 단위는 모름 → 안전한 쪽)
- 글 전체가 한도 이하면 아무것도 바꾸지 않는다. 넘을 때만 나눈다
- 묶음 줄 중간은 자르지 않는다. 줄 경계에서, 앞 메시지를 한도까지 채우고 넘긴다
- 이어지는 메시지는 칸 제목을 `(이어서)`를 붙여 다시 쓴다. 칸 제목 없이 줄만 있으면 새로 생긴 실패를 계속 남은 실패로 읽을 수 있다(1순위 위험)
- 보관 파일은 나누지 않는다(비교는 묶음 단위라 글 모양과 무관)

## 4. 비목표 (만들지 않을 것 — AI가 끼워 넣을 때 가리킬 근거)
- 사라진 실패 표시(F5), 사이 밤의 실패 확인(F6) (인터뷰 4회차)
- 메신저 자동 게시, 설계팀 자동 통보, 메일 발송 — 사람이 붙여 넣는다 (workflow.md 5~6단계)
- 위키 "알려진 실패" 표 읽기·연동 (constraints.md 금지)
- 실패 원인 분석, 담당자 배정, 대시보드·HTML·웹 화면
- 설정 파일, 옵션 플래그(색상·출력 형식 선택·기준 날짜 수동 지정 등), 플러그인 구조
- 로그인·권한, 캐시, 재시도, 병렬 처리, 다국어, 다중 사용자 동시 쓰기, 보관 결과 잠금
- 외부 패키지(pip 불가), Python 3.7+ 전용 기능(`dataclasses` 등)
- 하위 폴더 재귀 탐색 (samples에 하위 폴더 없음)
- 보관 결과의 오래된 파일 정리·백업
- 나눠 올리기의 한도 지정 옵션, 메시지별 파일 따로 쓰기, 메신저 자동 분할 게시 (F7은 표준출력에 구분 줄만 넣는다)
- 묶음 줄 하나가 혼자 4000바이트를 넘는 경우(첫 에러 줄은 140~175자라 사실상 없음) — 자르지 않고 그 메시지만 한도를 넘긴다

## 5. 제약
- 데이터: `/proj/soc/regress/<YYYY-MM-DD>/<테스트이름>__s<seed>.log`, 하위 폴더 없음, 날짜 = 회귀를 시작한 밤. 하룻밤 약 300개(60종 × seed 5), 실패 40개+ 날 있음 (constraints.md, log-format.md)
- 에러 줄 모양·함정: `domain/log-format.md`
- 실행 환경: 사내 리눅스 서버 터미널, 인터넷 없음, **Python 3.6 표준 라이브러리만**, bash/grep/awk 사용 가능 (인터뷰 2회차)
- 서버 로캘이 UTF-8이 아닐 수 있다 → 출력·보관 파일은 로캘과 무관하게 UTF-8 (가정)
- 하루 1회, 1명 실행. 동시 쓰기 없음 (인터뷰 1회차)
- 메신저 한 메시지 4000자 이하. 메신저가 막는 정해진 한도이고, 별도의 "읽기 편한 길이" 기준은 없다 (인터뷰 확인, 5·6회차). 넘는 날은 드물지만 원인이 많은 날 넘을 수 있다. 묶음 한 줄은 samples 기준 140~175자 → 한 메시지에 묶음 약 20개
- 보관 결과: 대리자도 같은 보관 폴더를 써야 하고, 비교 기준이 실제 마지막 게시 결과와 어긋나면 안 된다 (인터뷰 4회차, D-003)

## 6. 성공 지표
- P0 완료 기준 3개가 모두 diff 0 (명령으로 확인)
- 아침 정리 10분 이내(목표, 기준선 30분~1.5시간). 도구 실행 자체는 300개 로그에서 수 초 (가정, 서버에서 미측정)
- 글 순서·모양이 담당자 방식 그대로: 끊긴 로그 → 새로 생긴 실패 → 계속 남은 실패, 묶음당 한 줄 (success.md)
