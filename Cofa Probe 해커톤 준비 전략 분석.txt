* Phase 3: 모듈별 위임 및 검증 루프 실행 (2:00 ~ 4:45)

3. Cofa Probe에서 'AI Native'하게 일하는 방법 (Deep Think)
Cofa Probe에서 상위 1% 점수를 받는 'AI Native' 워크플로의 핵심은 "AI에게 코드를 짜게 하는 것"이 아니라 "20여 개의 평가 에이전트에게 나의 의도(Intent), 통제력(Steering), 검증 루프(Verification)를 증명하는 것"입니다. 구체적으로 다음 4단계 루프로 일해야 합니다.
① 페르소나 에이전트 공략법: '바텀업(Bottom-up) 맥락 수집 → 가설 검증' 대화법
우측 채팅창의 현업 페르소나 에이전트는 한 번에 정답을 주지 않습니다 [19:28].
* Bad (감점 패턴): "안녕하세요, 이번 과제에서 제가 구현해야 할 핵심 기능 리스트를 정리해 주세요." [16:52]
* Good (AI Native 패턴):
   1. 현업 관찰 질문 (사소한 맥락부터): "현재 선수들과 인터뷰 연습을 하실 때 가장 시간이 많이 걸리거나 불편한 단계가 어디인가요? 평소 코칭하실 때 메모는 어떤 식으로 남기시나요?" [16:37]
   2. 엣지 케이스 및 제약 조건 확인: "선수들이 혼자 연습할 때 한 번에 몇 명 정도 접속하나요? 과거 답변 기록을 수정하는 기능보다 직전 답변을 바로 비교해 보는 기능이 더 시급한가요?"
   3. 가설 확인 (구조화): "말씀해주신 내용을 바탕으로 핵심 플로우를 A → B → C로 정의하고, 당장 불필요한 D 기능은 제외하려 하는데 현업 니즈에 부합할까요?"
이렇게 끌어낸 대화 내용을 그대로 복사해 터미널의 AI에게 넘기지 말고, 내가 직접 소화하여 구조화된 SPEC.md와 CONSTRAINTS.md로 정리한 뒤 AI의 컨텍스트로 주입하세요. 이것이 평가 에이전트가 가장 높게 평가하는 '문제 정의 역량'입니다 [13:51].
② 의도(Intent) 극대화: '티키타카 설계'와 '서브 에이전트 위임'의 분리
조정석 엔지니어님이 밝힌 프로브의 '의도' 채점 기준은 대화형 설계와 장기 실행 위임의 분리입니다 [23:30].
* 설계 단계 (직접 스티어링): 아키텍처, 데이터 스키마, 비즈니스 로직의 경계 조건은 AI에게 바로 코드 작성을 시키지 말고 플랜 모드(Plan mode)나 대화를 통해 *"이 요구사항을 처리할 수 있는 가장 단순한 구조 2가지를 비교해 줘"*라고 물으며 내가 최종 선택을 내립니다.
* 구현 단계 (서브 에이전트 오케스트레이션): 설계가 확정된 보일러플레이트 작성, UI 컴포넌트 마크업, 단위 테스트 작성 등 시간이 걸리는 작업은 명확한 입출력 명세를 주어 서브 에이전트나 병렬 태스크로 분리해 위임합니다 [23:46].
* 코스트 엔지니어링(Cost Engineering): 한 세션에 모든 컨텍스트를 누적하면 토큰 비용이 기하급수적으로 늘어나고 AI의 성능이 저하됩니다. 작업 단위가 끝날 때마다 세션을 정리하거나 필요한 파일만 참조하게 하여 '적은 토큰으로 높은 완성도를 내는 그래프'를 그려야 합니다 [21:36].
③ 인지(Cognition) 극대화: AI의 오버엔지니어링에 '의도적 브레이크' 걸기
프로브의 평가 에이전트는 지원자가 AI에게 끌려다니는지, 아니면 주도권을 쥐고 있는지 프롬프트 로그와 코드에서 증거를 찾습니다 [28:29]. 작업 중 반드시 다음과 같은 '스티어링(Steering) 흔적'을 남기세요.
* 불필요한 복잡도 제거 지시: AI가 코드를 생성했을 때 *"지금 우리 요구사항에서는 동시 쓰기(Write) 충돌이 발생할 일이 없으니, 네가 추가한 복잡한 락(Lock) 로직과 별도 큐(Queue) 구조는 제거하고 단순 트랜잭션으로 축소해"*라고 명시적으로 지시합니다 [25:36].
* 코드 리뷰 및 역질문: AI가 낯선 디자인 패턴이나 라이브러리를 썼다면 그냥 넘어가지 말고 *"이 부분에 왜 이 패턴을 적용했는지 설명해 줘. 더 직관적인 방식으로 바꾸면 어떤 문제가 생기는지 알려줘"*라고 물어 이해한 뒤 넘어가야 합니다 [24:26]. 이 과정이 고스란히 로그에 남아 인지 점수를 높이고 사후 Q&A의 완벽한 답변 근거가 됩니다.
④ 클로즈드 루프(Closed-loop) 검증 자동화
AI Native하게 일한다는 것은 "사람이 눈으로 버그를 찾는 시간을 줄이고, AI가 스스로 검증할 수 있는 환경을 만들어주는 것"입니다 [06:29].
* 기능을 하나 구현할 때마다 AI에게 *"이 기능이 요구사항대로 작동하는지 검증할 수 있는 더미 데이터셋과 자동 테스트 스크립트(API 호출 및 상태 검증)를 먼저 짜고, 네가 직접 실행해서 통과할 때까지 수정해"*라는 클로즈드 루프를 걸어두세요.

① 토큰 비용(Cost Engineering)과 후반부 지능 저하 방지
앞서 영상에서 크래프톤 팀이 밝혔듯 "잘하는 참가자일수록 토큰 비용을 적게 쓴다"는 것이 핵심 지표입니다. 최상위 폴더에서 단일 세션으로 프로젝트 전체를 돌리면, 작업 시작한 지 2시간만 지나도 프론트엔드 UI 코드와 백엔드 DB 로직이 한 컨텍스트에 뒤섞입니다. 이 상태에서는 사소한 버그 하나를 고칠 때도 수만 토큰이 매번 소모되며, 컨텍스트가 길어질수록 모델의 추론 정확도가 떨어져 후반부 3시간을 수동 디버깅으로 날리게 됩니다.
② Cofa Probe의 '의도(Intent)' 루브릭 직격
조정석 엔지니어님이 인터뷰에서 직접 언급한 고득점 포인트는 "문제가 일어날 것 같은 세부 설계는 AI와 대화하며 직접 잡고, 롱텀하게 일임할 수 있는 구현은 서브 에이전트로 빼서 맡기는 AI 오케스트레이션"입니다. 또한 구한모 PO님 역시 "동시에 세션 5~6개를 환영분신술처럼 돌려 각각의 에이전트가 공용 마크다운(옵시디언) 메모리를 참조하게 한다"고 밝혔습니다. 즉, 프로브를 만든 제작진 자체가 '분할 실행 + MD 파일 기반 상태 공유'를 AI Native의 정답으로 정의하고 있습니다.
③ 평가 에이전트(20여 개)에게 완벽한 채점 근거 제공
에이전트 간 협업을 위해 작성한 SPEC.md, API_CONTRACT.md, DECISIONS.md 파일들은 에이전트들의 길잡이 역할을 할 뿐만 아니라, 코파 프로브의 20여 개 평가 에이전트가 소스 코드를 검사할 때 "이 지원자가 어떤 의도와 기준으로 시스템을 설계하고 통제했는가"를 증명하는 결정적 채점 근거가 됩니다.
3. 왜 '통신(IPC)'이 아니라 '마크다운(MD) + 스키마 파일'이어야 하는가?
제한된 해커톤 시간 내에 에이전트끼리 실시간 메시지를 주고받는 통신 구조를 짜면 ① 세팅 시간 손실, ② 에이전트 간 불필요한 핑퐁으로 인한 토큰 증발, ③ 어디서 스펙이 어긋났는지 사람이 추적하기 어려운 블랙박스화(인지 부채 발생)라는 3중고를 겪게 됩니다.
반면 마크다운(MD)과 정적 스키마 파일을 '단일 진실 공급원(Single Source of Truth, SSOT)'으로 삼는 파일 시스템 기반 협업은 다음과 같은 강점이 있습니다.
* 결정론적(Deterministic) 통제: 사람이 중간에서 API_CONTRACT.md의 내용을 승인·수정한 뒤 각 에이전트에게 작업을 지시하므로, AI에게 주도권을 뺏기지 않는 컨트롤러빌리티(Controllability)가 100% 보장됩니다.
* 이종 툴 간 완벽한 호환: Claude Code, Codex, Antigravity 등 서로 다른 AI 툴을 동시에 쓰더라도 별도의 연동 개발 없이 같은 폴더 내의 .md 파일만 읽고 쓰게 하면 즉시 협업이 성립합니다.
4. 실전 해커톤용 '1 아키텍트 + N 워커' 디렉토리 및 실행 설계
해커톤에서는 최상위(Root)를 관리하는 1개의 설계/통합 세션과 하위 디렉토리를 전담하는 2~3개의 구현 세션(또는 서브 에이전트)으로 나누어 운영하는 것이 가장 이상적입니다.

1. Root 아키텍트 & 오케스트레이터 (터미널 1 - 프로젝트 루트 실행):

   * 핵심 지침: 직접 무거운 구현 코드를 짜지 않고, 계약서(02_API_CONTRACT.md)를 확정하는 데만 집중합니다.
2. Backend 워커 (터미널 2 - /backend 디렉토리에서 실행 또는 서브 에이전트 위임):
   * 역할: ../docs/02_API_CONTRACT.md와 ../shared/만 읽고 API, DB, 비즈니스 로직과 단위 테스트를 구현합니다.
   * 토큰 절약 포인트: 프론트엔드의 수많은 UI 컴포넌트 파일을 전혀 읽지 않으므로 토큰 소모가 1/3 이하로 줄어들고 속도도 매우 빠릅니다.
3. Frontend 워커 (터미널 3 - /frontend 디렉토리에서 실행 또는 UI 특화 에이전트):
   * 역할: 백엔드가 완성되기를 기다리지 않고, ../docs/02_API_CONTRACT.md에 정의된 JSON 응답 규격을 바탕으로 Mock 데이터를 만들어 UI와 상태 관리를 병렬로 구현합니다.
   * 연동: 백엔드 워커가 03_TASK_BOARD.md에 API 구현 및 테스트 완료를 기록하면, 그때 API 엔드포인트만 실제 서버로 연결합니다.
5. 분할 작업 시 반드시 지켜야 할 3가지 실패 방지 원칙
방식 B를 쓰다가 실패하는 유일한 이유는 '프론트와 백엔드를 나중에 합칠 때 스펙이 안 맞아서 터지는 통합 지옥(Integration Hell)' 때문입니다. 이를 막으려면 다음 3가지를 철칙으로 삼아야 합니다.
1. Contract-First (계약 확정 전 분할 금지): 02_API_CONTRACT.md와 공용 데이터 스키마가 확정되기 전에는 절대로 백엔드와 프론트엔드 세션을 동시에 돌리지 마세요. 첫 1시간 반 동안 루트에서 계약을 단단히 고정하면 이후 3시간의 병렬 구현은 레고 블록처럼 한 번에 맞물립니다.
2. 계약 변경 권한의 단일화 (Read-Only Rule): 구현 도중 백엔드나 프론트엔드 에이전트가 마음대로 API 스펙을 바꾸지 못하게 각 폴더의 CLAUDE.md에 "API 스펙 변경이 필요하면 임의로 수정하지 말고 03_TASK_BOARD.md의 Blocker 섹션에 보고하고 멈출 것"이라고 못 박아 두세요. 스펙 수정은 반드시 내가 인지한 상태에서 승인해야 '인지(Cognition)' 점수를 지킬 수 있습니다.
3. 1시간 주기의 통합 체크포인트: 작업 종료 30분 전에 처음 합치려 하면 반드시 에러가 납니다. 기능이 1~2개 완성될 때마다 루트 세션에서 백엔드 서버와 프론트엔드 화면을 실제로 띄워 내장 브라우저로 동작을 확인하는 짧은 검증 루프를 돌리세요.

[요구사항 발생 / 코드 수정 필요]
      │
      ├── Case 1: 단일 모듈 내부 로직 수정 (입출력 포맷·계약 변경 없음)
      │     └─> 해당 <module>/ 세션 단독 실행
      │           ├─ 1) 실패 재현 테스트 또는 샘플 픽스처 검증 먼저 실행
      │           ├─ 2) 모듈 내부 코드만 수정 (타 디렉토리 열람 금지)
      │           └─ 3) 로컬 검증 통과 후 docs/03_TASK_BOARD.md 상태 업데이트
      │
      └── Case 2: 모듈 간 인터페이스 변경 필요 (파일 포맷, CLI 옵션, 스키마, API 변경)
            └─> 하위 모듈에서 임의 수정 절대 금지!
                  ├─ 1) 하위 에이전트가 docs/03_TASK_BOARD.md 에 [BLOCKER] 등록 후 대기
                  ├─ 2) Root 세션에서 docs/02_INTERFACE_CONTRACT.md 및 shared/ 스키마 갱신
                  ├─ 3) 변경 이유를 docs/04_DECISIONS.md 에 기록
                  └─ 4) 관련된 각 <module>/ 세션에 "갱신된 계약서를 읽고 반영하라"고 병렬 지시

핵심 운영 팁 3가지
1. 상용 툴/외부 환경 의존성 분리 (Fixture-First): EDA 툴 제어기나 자동화 러너(Archetype B)를 개발할 때는 먼저 docs/02_INTERFACE_CONTRACT.md에 "입력 설정 파일 구조", "생성되어야 할 제어 스크립트(예: .tcl, .sh) 규격", "파싱해야 할 표준 출력/로그 샘플"을 정의해 두세요. 그러면 실제 무거운 EDA 툴을 매번 돌리지 않고도 에이전트가 1초 만에 드라이런(Dry-run) 검증 루프를 돌며 정확한 코드를 작성할 수 있습니다.
2. 수정 전 '영향 범위 브리핑' 강제: 버그를 고치거나 기능을 바꿀 때 바로 코드를 고치게 하지 말고, *"수정하기 전에 원인과 수정할 파일/함수 목록을 3줄로 먼저 보고해"*라고 지시하여 불필요한 오버엔지니어링(과도한 추상화, 시키지 않은 아키텍처 변경)을 사전에 차단하세요.
3. 작업 단위 완료 후 /clear (컨텍스트 초기화): 모든 설계 계약과 진행 상태가 docs/01~04.md에 기록되어 있으므로, 모듈에서 기능 하나를 완성하거나 버그 하나를 잡은 뒤에는 세션을 /clear로 비우세요. 항상 가벼운 컨텍스트 상태를 유지해야 에이전트의 추론 속도와 코드 정확도가 최상으로 유지됩니다.
