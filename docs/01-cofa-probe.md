# Cofa Probe 이해하기

> 출처: 크래프톤 AI 프론티어 본부 구한모 PO·조정석 AI 프로덕트 엔지니어의 인터뷰 영상(https://www.youtube.com/watch?v=CLpN3zl8noQ) 요약과, 이를 바탕으로 Gemini와 나눈 분석 대화(`Cofa Probe 해커톤 준비 전략 분석.txt`).
> 2차 정보다. 당일 안내로 반드시 확인할 항목은 맨 끝 8절에 모았다.

## 1. 한 줄 정의
Cofa Probe(코파 프로브)는 크래프톤이 만든 **AI 기반 실무 역량 평가 솔루션**이다. 알고리즘 코딩 테스트 대신, 지원자가 **AI와 함께 일하는 전 과정**을 웹 IDE 안에서 관찰하고 20여 개의 평가 에이전트가 채점한다. 채용 평가와 해커톤(코파톤) 양쪽에 쓰인다.

## 2. 왜 만들었나 — 철학
| 개념 | 뜻 | 우리에게 의미 |
|---|---|---|
| AI 리터러시 | 기존 워크플로 안에서 AI 도구로 효율을 높이는 수준 | 이것만으로는 상위권이 안 된다 |
| AI 네이티브니스 | 제로 베이스에서 워크플로 자체를 재설계하고, 명확한 의도로 도구를 직접 만들어 문제를 푸는 태도 | 평가가 보려는 것 |
| "코드를 사랑하는 사람은 뽑지 않는다" | 끝까지 직접 짜겠다는 에고, 아름다운 코드·픽셀 집착보다 검증된 외부 자산을 가져와 빨리 팔 수 있는(sellable) 결과를 내는 사람 | 직접 짜는 시간을 줄이고 설계·검증·지휘에 쓴다 |
| 채용의 이상 = "하루 같이 일해 보기" | 코딩 테스트는 그 대용품이었고, 프로브는 그 이상에 더 가깝게 만든 것 | 시험이 아니라 **하루치 업무**처럼 행동한다 |

제작진 자신의 일하는 방식이 평가 기준의 힌트다.
- 엔지니어(조정석): 하루 대부분을 직접 코딩이 아니라 "에이전트에게 시킬 **작업 범위와 검증 루프** 설계"에 쓴다. 퇴근할 때 에이전트 4~5개를 동시에 돌려 놓고 다음 날 결과를 확인한다.
- PO(구한모): 옵시디언 파일 트리와 크론잡으로, 어떤 모델을 쓰든 **같은 메모리와 스킬을 참조하는 공용 저장소**를 만들었다. 주말 하루를 투자(CapEx)해 매일의 판단 비용(OpEx)을 줄인다.

## 4. 어떻게 평가하나
- **글래스박스 과정 심사.** 발표용 데모가 없다. 입력한 모든 프롬프트, 페르소나와의 채팅 로그, 도구 설정, 검증 명령, 토큰 사용 곡선, 화면 스크린샷, 내부 실행 상태, 사후 Q&A 답변을 20여 개 에이전트가 병렬로 대조해 리포트를 만든다.
- **세 가지 축** (기술 부채·의도 부채·인지 부채 개념에서 착안했다고 설명):

| 축 | 보는 것 | 감점 사례 |
|---|---|---|
| 기술 (Technique) | 결과물 완성도, 아키텍처, 사용한 스킬, 화면 스크린샷, 내부 실행 상태 | 실제로 동작하지 않거나 구조가 무너진 결과물 |
| 의도 (Intent) | AI 핸들링과 오케스트레이션. 문제를 쪼개고, 세부 설계는 대화로 다듬고, 구현은 서브에이전트에 위임하는 주도성 | 과제 지시서를 통째로 복사해 AI에게 위임 |
| 인지 (Cognition) | AI가 만든 코드와 패턴을 **왜** 택했는지 이해하고 설명하는가. AI의 과잉 설계를 통제하는가 | 읽기만 필요한 API에 AI가 넣은 쓰기 가드를 그대로 둬 부하를 유발 (주도권 상실) |

- **토큰은 지표다.** 상위권일수록 토큰을 적게 쓴다. 초반에 과제를 통째로 넣고 "다 구현해 줘"를 하면 10분 만에 그럴듯한 결과가 나오지만, 이후 3시간을 수동 수정에 쓰며 토큰을 다 태운다.
- **사후 Q&A와 면접.** 제출 후 질문에 답해야 하고, 상위권은 면접에서 결정 이유를 집요하게 묻는다.

## 5. 네 가지 구조적 특징 — 게임의 법칙
1. **방탈출형 문제 정의.** README는 일부러 짧고 모호하다. 진짜 요구사항과 제약은 페르소나와 대화해야 하나씩 열린다. "제가 당장 해야 할 일을 1, 2, 3으로 알려주세요"는 막혀 있다. 사소한 현장 맥락 질문에서 시작해 고도화할수록 점수가 높다.
2. **결과물이 아니라 과정 심사.** 마지막 5분 데모로 뒤집을 수 없다. 6시간 내내 남는 로그가 채점 근거다.
3. **AI의 과잉 친절이 함정.** 최신 모델은 시키지 않아도 엔터프라이즈급 구조와 추상화를 넣는다. 이를 비판 없이 받았는지, 요구사항에 맞게 쳐냈는지를 인지 점수와 Q&A에서 판다.
4. **외부 무기 반입이 합법.** 맨손이 공정하다고 보지 않는다. 준비해 온 하네스를 쓰는 참가자에게 오히려 가중치를 준다.

## 6. 실제 사례와 인사이트
- **비개발자의 상위권 입상.** CJ올리브영과 진행한 코파톤에서 매장 2년 근무 출신, 개발 경험이 전혀 없는 참가자가 상위권에 올랐다. 뷰티 커머스 고객 입장에서 무엇이 중요한지 **도메인 지식을 설계에 정확히 녹여** AI 역량과 결합했기 때문이다. 도메인 지식을 구조화해 AI에 주입하는 능력이 코딩 능력보다 변별력이 크다.
- **10분의 유혹.** 통째로 위임한 결과물은 그럴듯하지만 고칠 수 없다. 느리게 시작하는 쪽이 끝에 빠르다.
- **검증 루프가 곧 AI 네이티브.** 사람이 눈으로 버그를 찾는 대신, AI가 스스로 검증할 수 있는 환경(테스트, 더미 데이터, 헬스체크)을 만들어 주는 것.
- **엔지니어 역할의 확장.** 스택 확장 → 풀스택 → 프로덕트 엔지니어 → FDE(현업에서 직접 배포·QA). 현업과 구현 사이를 메우는 사람을 찾는다.

## 7. 우리에게 주는 결론 — 남겨야 할 증거
| 평가가 보는 것 | 우리가 남길 증거 | 만드는 도구 |
|---|---|---|
| 문제 정의 능력 | 바텀업 인터뷰 질문 로그, 그것을 소화한 `docs/domain/`, `GLOSSARY.md`, `SPEC.md`의 비목표 | `/kickoff` `/interview` `/spec` |
| 쪼개고 지휘 (의도) | `SPEC.md` 8절 입출력 샘플(모듈이 여럿이면 `CONTRACT.md`), `TASKS.md`의 슬라이스, `docs/briefs/`의 위임 브리프, 서브에이전트 사용 로그 | `/spec` `/delegate` |
| 검증 루프 (기술) | 슬라이스별 검증·회귀 확인 로그, 통합 체크포인트, 깨지지 않은 화면 | `/delegate` `/wrapup` |
| 과잉 설계 통제 (인지) | diff 감사 기록, 거절한 AI 제안이 자동으로 적힌 `DECISIONS.md`, `shortcut:` 주석 | `/delegate` `/wrapup` |
| 이해와 설명 (인지, Q&A) | `RETRO.md`의 결정·대안·트레이드오프·예상 질문, 대화 로그에 남는 다지기 문답과 퀴즈 | `/interview` `/wrapup` |
| 토큰 효율 | 짧은 CLAUDE.md, 호출 전에는 비용 0인 스킬, 파일 기반 메모리와 `/clear`, 필요한 파일만 읽는 규칙 | 하네스 구조 전체 |
