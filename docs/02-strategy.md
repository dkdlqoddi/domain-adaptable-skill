# 해커톤 전략 — Cofa Probe 환경에서 Claude Code로 일하는 법

> 전제: 6시간, 1인, 웹 IDE + 터미널(Claude Code) + 내장 브라우저 + 페르소나 채팅. 과제 도메인은 당일까지 모른다.
> 이 문서는 "왜"와 "순서"를 설명한다. 당일 손에 들 한 장은 [03-cheatsheet.md](03-cheatsheet.md), 평가 방식은 [01-cofa-probe.md](01-cofa-probe.md).
> 설치·충돌·도구별 명령의 현재 사용법은 [README의 표](../README.md#준비와-설치-터미널)를 따른다. Codex는 스킬을 `$이름`으로 호출하고 컨텍스트는 `/new`로 비운다.

## 0. 한눈에
1. **첫 1시간은 코딩 금지.** 인터뷰로 숨은 요구사항을 열고 `docs/`에 내 말로 적는다.
2. **계약을 먼저 고정**하고(`SPEC.md` 8절의 입출력 샘플, 모듈이 여럿이면 `CONTRACT.md`), 그 다음에만 만든다.
3. **슬라이스 하나씩** 브리프로 위임하고, 검증 명령으로 닫힌 루프를 돈다.
4. **AI가 끼워 넣은 것은 쳐내고, 쳐낸 기록을 남긴다.**
5. **메모리는 파일에, 세션은 가볍게.** 슬라이스가 끝나면 `/clear`.

## 1. 원칙 다섯 가지와 근거
| 원칙 | 왜 (Probe가 보는 것) | 어디에 구현됐나 |
|---|---|---|
| 코딩 전 문제 정의 | 요구사항은 인터뷰로만 열린다. 바텀업 질문이 고득점, 지시문 통째 위임은 감점 | `/kickoff` → `/interview` 반복 → `docs/domain/`, `GLOSSARY.md` |
| 계약 먼저, 병렬은 그 다음 | 병렬 작업이 실패하는 유일한 이유는 합칠 때 인터페이스가 안 맞아서. 제작진 스스로 "MD 공용 메모리 + 다중 세션"으로 일한다 | `/spec` → SPEC 8절(또는 `CONTRACT.md`) + `fixtures/` |
| 슬라이스 위임 + 닫힌 루프 | "쪼개고 위임하고 검증"이 의도 점수. 수동 수정은 토큰과 시간을 태운다 | `/delegate`(위임 → 루트 재검증 → 회귀 확인) |
| 과잉 설계는 쳐내고 기록 | AI 제안의 무비판 수용은 인지 감점. 거절 기록은 가점과 Q&A 근거 | `CLAUDE.md` 사다리 + `/delegate`·`/wrapup`의 정리 단계 + 결정 자동 기록 |
| 파일 메모리, 가벼운 세션 | 토큰 곡선이 지표. 긴 컨텍스트는 느리고 부정확하다 | `docs/` 단일 진실 공급원 + `/clear` + 서브에이전트 |

## 2. 세션 구조: 설계자 1 + 워커 N
```
        ┌──────────────── 루트 세션 (프로젝트 루트에서 claude) ─────────────────┐
        │ 역할: 인터뷰 소화 · SPEC/CONTRACT 확정 · 브리프 작성 · 통합 검증 · 결정 기록 │
        │ 읽는 것: CLAUDE.md(항상) + TASKS.md, SPEC P0(시작 시) + 그때그때 필요한 파일 │
        └──────┬──────────────────────┬──────────────────────┬────────────────┘
               │ 브리프(Agent 도구)     │ 브리프                 │ (선택) 터미널 하나 더
        ┌──────▼──────┐        ┌──────▼──────┐        ┌──────▼──────────┐
        │ 서브에이전트  │        │ 서브에이전트  │        │ 모듈 세션         │
        │ 새 컨텍스트   │        │ 새 컨텍스트   │        │ cd <모듈> && claude │
        │ 쓰기: 모듈A/  │        │ 쓰기: 모듈B/  │        │ 쓰기: <모듈>/     │
        └──────┬──────┘        └──────┬──────┘        └──────┬──────────┘
               └──── 상태 공유는 파일로만: docs/TASKS.md · CONTRACT.md · fixtures/ ────┘
```
- 서브에이전트는 매번 **새 컨텍스트**로 시작한다. 루트 대화가 길어져도 구현 품질이 떨어지지 않고, 루트는 브리프와 보고만 주고받으므로 토큰이 적게 든다.
- 모듈 세션(터미널 추가)은 한 모듈이 20분 이상 독립적으로 돌아갈 때만 연다. 그 폴더에서 `claude`를 띄우면 루트 `CLAUDE.md`와 그 폴더의 `CLAUDE.md`가 함께 로드된다.
- 에이전트끼리 직접 통신시키지 않는다. 세팅 시간, 핑퐁 토큰, 추적 불가능한 블랙박스라는 삼중고다. 협업은 `TASKS.md`와 `CONTRACT.md`로만.

## 3. 타임박스 (6시간 기준, 비율 1/6 · 1/6 · 11/24 · 5/24)
| 시간 | 단계 | 목표 | 명령 | 산출물 | 하지 말 것 |
|---|---|---|---|---|---|
| 0:00–0:10 | 세팅 | 하네스 설치, 과제 재정의 | 설치, `/kickoff` | `docs/` 뼈대, 모르는 것 목록 | 코드 열람 |
| 0:10–1:00 | 탐색 | 인터뷰(보통 3~4회차, 필요하면 더), 내 말로 다지기 | `/interview` ↔ 페르소나 (끝나면 이어서 다지기·요약·퀴즈) | `domain/*.md`, `GLOSSARY.md`, SPEC 초안 | 아키텍처 논의 |
| 1:00–1:30 | 계약 | P0 ≤ 3, 비목표, 입출력 샘플, 슬라이스 | `/spec` | `SPEC.md`, `fixtures/`, `TASKS.md` (모듈이 여럿이면 `CONTRACT.md`·모듈 CLAUDE.md) | 기능 추가 |
| 1:30–2:00 | 뼈대 | 끝까지 지나가는 S0 | `/delegate S0` | 돌아가는 뼈대 | 예쁘게 만들기 |
| 2:00–4:45 | 구현 | P0 슬라이스 반복 | `/delegate` → `/clear` | 동작하는 P0, DECISIONS | P1부터 손대기 |
| 슬라이스마다 | 회귀 확인 | 끝난 슬라이스가 안 깨졌나 | `/delegate`에 포함 | 체크포인트 기록 | 건너뛰기 |
| 4:45–6:00 | 마무리·복기 | 통합 검증, 잔재 정리, 화면 확인, README, Q&A 대비 | `/wrapup` 한 번 (check → retro → 퀴즈) | 깨끗한 저장소, `RETRO.md` (퀴즈는 파일 없음) | 새 기능 |

`/kickoff README.md 13:00`처럼 마감 시각을 주면 지금부터 마감까지를 같은 비율로 나눈다(설치에 쓴 시간이 빠진다). `4h`처럼 시간을 주면 남은 시간으로 본다. 2차 예선(4시간)이면 탐색 0:00–0:40 → 계약·뼈대 0:40–1:20 → 구현 1:20–3:10 → 마무리 3:10–4:00.

## 4. 페르소나 인터뷰: 바텀업 → 가설 검증
### 사다리 (한 묶음 = 한 칸, 질문 3~5개)
① 현장 관찰 → ② 페인포인트 → ③ 데이터·제약 → ④ 성공 기준 → ⑤ 가설 확인("A→B→C로 보고 D는 빼려는데 맞나요?")

### 나쁜 질문 → 좋은 질문
| 나쁜 질문 | 왜 나쁜가 | 고친 질문 |
|---|---|---|
| "이번 과제에서 구현할 핵심 기능 리스트를 정리해 주세요" | 답하지 않게 막혀 있고, 문제 정의를 넘긴 것으로 기록된다 | "지금 선수들과 인터뷰 연습을 하실 때 가장 시간이 많이 걸리는 단계가 어디인가요?" |
| "DB는 뭘 쓰면 되나요?" | 현업은 모른다. 기술 결정은 내 몫이다 | "답변 기록은 지금 어디에 남기세요? 나중에 다시 보시나요?" |
| "실시간 기능이 필요한가요?" | 예/아니오로 끝나고 맥락이 없다 | "선수가 답하고 나서 피드백을 언제 받는 게 가장 도움이 되나요? 바로? 끝나고 한꺼번에?" |

### 답변 다루기
- 복붙 금지. 페르소나의 답은 `/interview <답>`으로 넘겨 사실·용어·제약·우선순위를 분리해 문서에 넣는다(다음 질문도 함께 나온다). 이 "소화" 과정이 로그에 남는 것이 문제 정의 역량의 증거다.
- 모순은 사람이 판단한다. AI가 임의로 한쪽을 택하게 두지 않는다.
- 보통 3~4회차면 ①~⑤가 채워진다. 그래도 P0·비목표·입출력·성공 기준을 바꿀 모르는 것이 남으면 보충 묶음으로 더 묻는다. 회차 제한은 없다.

### 멈추는 기준
①~④가 채워지고 ⑤ 가설을 현업이 확인했고, 중요한 모르는 것이 남지 않았으면 멈춘다. 1단계 마감이 지나도 끊지 않는다. 질문 묶음에 `1단계 마감 +N분`이 붙으니 보고 판단한다(길어진 만큼 구현 시간이 준다). 사소한 의문은 "아직 모르는 것"에 두고 구현 중 한 번 더 물으면 된다. 멈추면 같은 명령이 이어서 다지기(빈틈을 사람에게 하나씩) → 요약 → 퀴즈를 한다.

### 샘플과 시연이 숨은 요구를 연다 (리허설 2)
- 과제가 샘플 데이터를 주면 ③ 칸을 묻기 전에 훑는다. 아무도 말하지 않은 예외(끊긴 로그)가 샘플에 있었고, 그것을 질문으로 바꾸자 담당자가 숨은 요구를 꺼냈다.
- S2 무렵 실제 출력을 한 번 보여 준다. 인터뷰 때는 안 나온 제약(메신저 4000자 한도)이 출력을 본 순간 나왔다.

## 5. 계약 우선과 최소 모듈
- **P0는 3개 이하.** 없으면 제출 불가인 것만. 각각 검증 가능한 완료 기준 한 줄.
- **비목표가 방패다.** 인증·권한·캐시·재시도·다국어·확장성·동시 쓰기 중 이번에 안 하는 것을 이름 붙여 적는다. AI가 끼워 넣을 때 이 줄을 가리킨다.
- **모듈은 최소로.** 기본은 1개다(리허설 2·3 모두 1개). 나누는 이유는 둘뿐: 검증 방법이 다르다, 병렬로 만들 가치가 있다. 모듈 분할 자체가 과잉 설계가 될 수 있다. 모듈이 1개면 계약은 SPEC 8절에 두고 `CONTRACT.md`는 만들지 않는다.
- **샘플 값이 곧 픽스처.** 계약에 적은 샘플 입출력을 `fixtures/`에 파일로 둔다. 모듈은 상대 코드를 열지 않고 이 파일로 개발·검증한다. 서로 기다리지 않고, 컨텍스트가 섞이지 않는다.
- **S0 = 걸어다니는 뼈대.** 하드코딩이어도 입력 하나가 끝까지 지나가는 것을 2:00 전에 만든다. 통합 지옥의 대부분이 여기서 사라진다.
- **범위 분리는 병렬일 때만.** S0 뒤 S1처럼 순차 작업은 같은 파일을 확장한다. 동시에 실행할 슬라이스만 의존성과 쓰기 범위가 없어야 한다.
- **도메인 무관.** 계약은 API·CLI·파일 포맷·함수·상태 전이 중 맞는 것으로 적는다. 웹·데이터 CLI·EDA 자동화 예시는 `spec/contract-examples.md`에 있다. 외부 도구·장비를 부르는 모듈은 실제 도구 없이 `--dry-run`(픽스처 재생)으로 끝까지 돌게 만든다.

## 6. 구현 루프
```
/delegate Sn (브리프 → 서브에이전트 구현 → 루트 재검증·회귀 확인 → 과잉 설계 정리 → TASKS 갱신 → 커밋) → /clear → 다음 슬라이스
```
### 수정 유형 매트릭스
| 유형 | 예 | 어디서 | 규칙 |
|---|---|---|---|
| A 모듈 내부 (계약 변경 없음) | 레이아웃 변경, 쿼리 최적화, 로컬 버그 | 그 모듈(서브에이전트 또는 모듈 세션) | 재현 → 수정 → 검증 → TASKS 갱신. 루트를 깨우지 않는다 |
| B 경계 교차 (계약 변경) | 새 필드 필요, 응답 구조 변경 | 루트 | 하위에서 임의 변경 금지. BLOCKER 등록 → 루트가 SPEC 8절(또는 `CONTRACT.md`)·`fixtures/` 갱신 → 결정 자동 기록 → 영향 슬라이스에 짧은 재위임 |
| C 통합 버그 | 연결했더니 400/500, 포맷 불일치 | 루트가 진단 → 어긴 모듈이 수정 | 계약과 실제 값을 대조해 **어긴 쪽만** 고친다. 계약을 고치지 않는다 |
| D 새 요구 | 시연을 본 담당자가 새 제약을 말함 | 루트 | `/interview <답>` → `/spec` 다시 실행(P0가 꽉 찼으면 P1부터, 입출력 샘플·픽스처 갱신, 슬라이스 추가, D-번호) → `/delegate` |

### 버그는 재현 먼저
에러 문구만 붙여 넣고 "고쳐줘"를 반복하면 AI가 원인을 모른 채 여러 파일을 추측으로 건드린다. 순서는 고정이다: 재현하는 최소 명령 → 원인·파일·검증 3줄 브리핑 → 최소 수정 → 재현 명령 재실행.

### 범위 이탈 가지치기
위임 결과가 돌아오면 `/delegate`가 `git status --short`와 diff를 훑는다. 브리프에 없는 것(방어 로직, 상태 관리 라이브러리, 폴백)이 들어왔으면 묶어서 제거를 제안하고, 고른 것은 `DECISIONS.md`에 자동으로 남는다. 거절 기록은 인지 점수로 바뀐다.

시작할 때 기존 변경·스테이징을 기록해 종료 상태와 비교한다. 기존의 범위 밖 변경은 보존하고, 새 변경의 출처가 불명확하면 경로를 알린다. 자동으로 되돌리지 않는다. 커밋은 검토한 개별 파일만 포함하고 기존 staged 작업이 있으면 보류한다. `/spec`·`/delegate`·`/wrapup` 모두 [공통 Git 절차](../harness/.claude/skills/delegate/git-workflow.md)를 따른다.

## 7. 과잉 설계 방어 (ponytail에서 차용)
- **항상 켜져 있는 것** (`CLAUDE.md` 12줄): 사다리 6칸(필요한가 → 이미 있나 → 표준 라이브러리 → 설치된 의존성 → 한 줄 → 최소 구현 + 작은 테스트), "설계는 최소로 범위는 끝까지", 절대 자르지 않는 목록(입력 검증·데이터 보호·보안·접근성·명시 요구), 코드를 바꾼 답의 끝 두 줄, `shortcut:` 주석.
- **왜 스킬이 아니라 CLAUDE.md인가.** 스킬은 모델이 알아서 꺼내 쓰지 않는 경우가 많다. 외부 테스트에서 ponytail을 스킬로만 설치하면 10세션 중 한 번도 자동 발동하지 않았고, 그래서 플러그인은 세션 시작 시 규칙을 주입한다. 항상 로드되는 곳에 짧게 두는 것이 확실하다.
- **두 시점.** 만든 후 `/delegate`가 슬라이스 diff를, 제출 전 `/wrapup`(check)이 저장소 전체를 본다. 만들기 전에는 `CLAUDE.md` 사다리가 항상 켜져 있다.
- **기록으로 전환.** 쳐낸 것은 `DECISIONS.md`에 "AI가 X 제안 → 거절, 이유"로 자동 기록된다. Probe에 맞춰 추가한 단계다.

## 8. 토큰 전략
### 하네스 추가량 (`scripts/check.sh`로 현재 값 확인)
| 항목 | 언제 로드되나 | 크기(근사) |
|---|---|---|
| 루트 `CLAUDE.md` | 매 세션 항상 | 80줄 이하 |
| 스킬 설명 5개 | 항상이지만, 전부 사용자 호출 전용(`disable-model-invocation`)이라 | 0 |
| 스킬 본문 1개 | `/명령` 호출 시, 이후 그 세션에 유지 | 120줄 이하 |
| 스킬 참고 파일 | 본문이 가리킬 때만 | 파일마다 80줄 이하 |
| 모듈 `CLAUDE.md` | 모듈이 여럿일 때, 그 폴더의 파일을 만질 때만 | 40줄 이하 |
| `docs/` 상태 파일 | 세션 시작 시 TASKS + SPEC P0만 | 과제에 따라 |

전체 세션 비용이 아니라 하네스가 더하는 양이다. 시스템 프롬프트·도구·기존 지침·대화 토큰은 별도다. `check.sh`는 줄 수 한도를 검사하고 바이트 수로 토큰을 추정하며, 실제 토큰 상한을 강제하지는 않는다.

### 규칙
1. 슬라이스가 끝나면 `/clear`. 상태는 `docs/`에 있다. 새 세션은 CLAUDE.md + TASKS + SPEC P0만 읽는다.
2. 구현은 서브에이전트로. 루트에 코드가 쌓이지 않는다.
3. diff만 읽는다. 저장소 전체 스캔 금지. `node_modules`·빌드 산출물·로그는 열지 않는다.
4. 인덱스 먼저: `domain/README.md`, `TASKS.md`를 보고 필요한 파일 하나만 연다.
5. 브리프에 값을 복사한다. 서브에이전트가 파일을 찾아 헤매지 않는다.
6. 질문은 한 번에 하나. 왕복이 줄어든다.

### 토큰을 태우는 패턴 (하지 말 것)
과제 통째로 + "다 만들어줘" · 에러 복붙 반복 · 6시간 한 세션 유지 · "코드베이스 전체를 파악해 줘" · 인터페이스 모듈 세션이 엔진 코드를 읽는 것 · 에이전트 간 직접 대화

## 9. 사후 Q&A·면접 대비
- `/wrapup`의 retro 단계가 `RETRO.md` 9절(무엇·흐름·구조·SPEC 대비·핵심 결정·거절한 AI 제안·지름길·다음 할 일·예상 질문 10개)을 문서에서 뽑는다.
- 예상 질문 유형: 왜 이 구조인가 / 대안은 / AI 제안 중 거절한 것은 / 어떻게 검증했나 / 시간이 더 있다면 / 토큰을 어떻게 아꼈나.
- `/wrapup`이 retro 뒤에 이어서 문서에서 쉬운 말 요약과 4문항 퀴즈를 만들어, 내가 설명할 수 있는지 확인한다. 결과를 파일에 남기지 않고 제출·푸시를 막지 않는다. 제출 뒤 면접 전에는 `/interview quiz`로 다시 풀면 된다.
- 검증 실패가 남으면 `/wrapup`이 고칠지, 실패를 RETRO 4절에 적고 진행할지 묻는다. 시간이 있으면 고친 뒤 `/wrapup`으로 검증부터 다시 한다. `/wrapup retro` 단독 호출도 통합 검증을 먼저 수행한다. 테스트 통과와 P0 전체 완료를 따로 확인한다.
- 설명 못 하는 코드는 지금 열어 본다. 모르는 코드를 제출하는 것이 최악이다.

## 11. 사전 준비 (CapEx — 당일 판단 비용을 줄이는 투자)
