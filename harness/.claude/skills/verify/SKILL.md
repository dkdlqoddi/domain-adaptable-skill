# /verify — 닫힌 루프 검증

## 왜
평가는 화면 스크린샷과 실제 실행 상태를 본다. "될 것 같다"는 점수가 아니다.
사람이 눈으로 버그를 찾는 대신 AI가 스스로 돌려보고 고치는 루프를 만들어야 후반 3시간을 지킨다.
마감 30분 전에 처음 합치면 반드시 터진다. 매시간 한 번씩 합쳐 본다.

## 절차
1. **대상**: `$ARGUMENTS`가 ID면 그 슬라이스, 비었거나 `all`이면 DOING·DONE 전부, `ui`면 화면 점검만.
2. `docs/TASKS.md`의 검증 명령을 **그대로 실행**한다. 없으면 먼저 가장 싼 것을 만들어 보드에 적는다(테스트 1개, curl 1줄, 픽스처 입력→출력 diff).
3. 결과 표: | 슬라이스 | 명령 | 결과 | 비고 |
4. **통합 확인** (`all`일 때):
   - 진입점을 1회 기동 → 헬스/첫 화면/첫 명령 응답 확인 → 종료.
   - 모듈 경계마다 CONTRACT의 샘플 값으로 1회 왕복(요청→응답, 파일 생산→소비).
5. **UI가 있으면** (`ui` 또는 `all`):
   - 빌드·린트 명령으로 컴파일 에러 확인. 빈 데이터·에러 상태를 렌더하는 코드가 있는지 확인(undefined 접근, 빈 목록).
   - 사용자에게 **내장 브라우저로 직접 볼 것**을 요청: 첫 화면, 핵심 흐름 1회, 빈 상태. 깨진 레이아웃·콘솔 에러·placeholder 문구는 감점 요인.
6. **실패 처리 (재현 먼저)**:
   ① 재현하는 최소 명령·테스트를 확보 → ② 원인·수정 파일·검증 방법 3줄 브리핑 → ③ 해당 모듈 범위 안에서만 최소 수정(또는 그 모듈에 위임) → ④ 재현 명령 재실행.
   - 어느 쪽이 계약을 어겼는지 판별한 뒤, 계약이 아니라 **어긴 쪽**을 고친다.
   - 에러 문구만 붙여 넣고 "고쳐줘"를 반복하지 않는다. 원인을 모르면 재현 범위를 더 좁힌다.
7. `docs/TASKS.md` 통합 체크포인트 표에 시각·결과 한 줄.

## 출력
결과 표 → 수정했으면 내역 → 마지막 줄 `확인하지 못한 것·리스크:`
