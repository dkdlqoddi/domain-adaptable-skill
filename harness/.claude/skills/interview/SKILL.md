# /interview — 숨은 요구사항 끌어내기

## 왜
페르소나 에이전트는 "제가 할 일을 1, 2, 3으로 알려주세요" 같은 질문에는 답하지 않게 되어 있다.
사소한 현장 맥락부터 시작해 점점 구체화하는 질문만이 진짜 요구사항을 연다.
받은 답변은 그대로 AI에 복사해 넣지 않고 **내가 소화해서** 문서로 만든다. 그 문서가 이후 모든 세션의 메모리이며, "문제를 정의했다"는 증거다.

## 모드
- `$ARGUMENTS`가 비었거나 `questions` → **질문 생성**
- `digest`로 시작하거나 답변 텍스트가 붙어 있음 → **정리**

## 질문 생성
1. 읽기: `docs/domain/README.md`(인덱스 + "아직 모르는 것"), `docs/SPEC.md` 7절. 다른 파일은 열지 않는다. 단, 과제가 샘플 데이터를 주었으면 ③ 칸을 묻기 전에 파일 목록과 한두 개만 훑는다. 샘플로 답이 나오는 것은 묻지 않고 `domain/`에 `(samples)`로 적는다. 샘플에는 있는데 아무도 말하지 않은 예외는 질문으로 바꾼다.
2. 아래 사다리에서 **아직 비어 있는 가장 낮은 칸**을 고른다. 한 묶음은 한 칸.
   ① 현장 관찰: 지금은 어떻게 하나, 어디서 시간이 가나, 무엇을 어디에 기록하나
   ② 페인포인트: 가장 불편한 순간, 실수가 나는 지점, 왜 아직 해결 안 됐나
   ③ 데이터·제약: 입력은 어디서 어떤 형식으로, 규모, 동시 사용자, 쓰기 충돌, 예외, 금지사항
   ④ 성공 기준: 무엇이 되면 "됐다"고 하나, 둘 중 하나만 된다면, 측정 지표
   ⑤ 가설 확인: "핵심 흐름을 A→B→C로 보고 D는 이번에 빼려는데 맞나요?"
3. 질문 3~5개를 표로:
   | # | 질문 (현업의 말로, 한 문장) | 왜 묻나 | 답을 적을 곳 |
   - 이미 문서에 답이 있는 것은 묻지 않는다. 기술 용어(API, DB, 스키마)를 질문에 쓰지 않는다.
   - 금지: 기능 목록을 대신 뽑아 달라는 질문, 예/아니오로 끝나는 질문의 연속.
4. 마지막 줄: "본인 말로 바꿔서 물어보세요. 답을 받으면 `/interview digest <답변>`."

## 정리 (digest)
1. 답변을 분리한다: 사실 / 용어 / 제약 / 우선순위 신호 / 새로 생긴 질문 / 기존 기록과의 모순.
2. 해당하는 곳에만, 짧게 쓴다:
   - 사실 → `docs/domain/<주제>.md`(persona·workflow·constraints·success 중 하나, 맞는 게 없으면 새 파일). 불릿 + `(인터뷰 N회차)`.
   - 용어 → `docs/GLOSSARY.md` 한 줄. **확정된 것만.** 한 단어가 두 뜻이면 분리를 제안한다.
   - 제약·우선순위 → `docs/SPEC.md` 3·5절에 `(인터뷰 확인)` 표시로 반영. 기능표는 후보로만 적고 P0 판정은 `/spec`에서.
   - 모순 → 문서를 고치지 말고 사용자에게 **하나씩** 보고(추천 해석 포함). 답을 받기 전에는 `domain/README.md`의 "아직 모르는 것"에 두 해석과 추천을 한 줄로 남긴다. `/clear` 뒤의 세션도 이어서 판단할 수 있게.
   - `docs/domain/README.md`의 요약 줄과 "아직 모르는 것"을 갱신.
3. 출력: 갱신한 파일(각 한 줄) → 판단이 필요한 것(있으면 하나, 추천과 함께) → 다음 묶음이 필요한지와 어느 칸인지.

## 멈추는 기준
①~④가 채워지고 ⑤ 가설을 현업이 확인했으면 멈추고 `/spec`으로 간다.
"더 물어볼 수 있다"는 이유로 계속하지 않는다. 상한은 전체 시간의 1/6.
