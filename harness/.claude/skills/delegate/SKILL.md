# /delegate — 슬라이스 하나를 끝까지

사용: `/delegate <슬라이스 ID 또는 한 줄 설명> [--parallel | --serial]` — 기본은 독립 TODO가 있으면 병렬, `--serial`은 지정 슬라이스만.

## 왜
"다 만들어줘"는 10분 만에 그럴듯한 결과를 주고, 남은 3시간을 수동 수정에 쓰게 만든다.
범위와 검증 방법이 적힌 브리프로 슬라이스 하나씩 위임하면, 서브에이전트는 깨끗한 컨텍스트에서 적은 토큰으로 정확히 만든다.
검증과 과잉 설계 정리를 같은 명령에서 끝내야 빠뜨리지 않는다. 브리프와 쳐낸 기록이 "쪼개고 지휘했다"는 증거다.

## 절차
시작 전에 [git-workflow.md](git-workflow.md)의 시작 상태를 확인한다. 기존 변경과 스테이징을 브리프에 남긴다.
1. **대상**: 호출 메시지의 ID를 `docs/TASKS.md`에서 찾는다. 설명만 있으면 새 행을 추가(쓰기 범위·검증 명령 포함)한 뒤 진행.
2. **재료** (이 파일들만 연다): 해당 슬라이스 행, `docs/SPEC.md`의 해당 기능 행·비목표·8절, 관련 `fixtures/`. 모듈이 여럿이면 `docs/CONTRACT.md`의 관련 절과 `<모듈>/CLAUDE.md`. 도메인 지식은 `docs/domain/README.md` 인덱스에서 고른 파일 1개까지.
3. **브리프**: [brief.template.md](brief.template.md) 형식으로 써서 `docs/briefs/<ID>.md`에 저장한다. 계약의 샘플 값은 링크가 아니라 **값을 그대로 복사**한다.
4. **알리고 바로 위임**: 두 줄(`위임: <ID> — <목표>` / 쓰기 범위·검증 명령·브리프 경로)만 보이고 5번으로 간다. 검증 명령·쓰기 범위가 비었거나, 병렬 범위가 겹치거나, 기존 변경과 작업 귀속이 불명확할 때만 하나를 묻는다(추천안 포함).
5. **위임**: 독립 TODO가 있으면 기본으로 [tmux.md](tmux.md)를 따라 `codex --yolo` 세션에 브리프·루트·모듈 지침 전문을 텍스트로 전달한다. `--parallel`도 같은 경로를 쓴다. 의존성이 모두 DONE이고 쓰기 범위·검증 자원이 겹치지 않는 작업만 기본 2개, 최대 3개 실행한다. **모든 보고를 회수하고 작업자를 멈춘 뒤** 6~8번을 슬라이스마다 처리한다. 실행 불가·독립 작업 없음·`--serial`이면 같은 브리프로 루트에서 순차 구현한다.
6. **검증** (루트에서 직접):
   - 보고된 검증 명령을 다시 실행한다. 보고만 믿지 않는다. 이전 DONE 슬라이스의 검증 명령도 함께 돌려 깨진 것이 없는지 보고, `docs/TASKS.md` 통합 체크포인트에 시각·결과 한 줄.
   - 실패하면 재현 먼저: 최소 재현 명령 → 원인·수정 파일·검증 방법 3줄 → 쓰기 범위 안에서 최소 수정(크면 실패 내용을 붙여 재위임) → 다시 실행.
   - 화면이 있는 슬라이스면 빌드 에러를 확인하고, 사람에게 첫 화면·핵심 흐름·빈 상태를 직접 봐 달라고 한 줄로 요청한다.
7. **정리** (과잉 설계):
   - `git diff -- <이번 슬라이스의 변경 파일들>`과 새 파일 내용을 검토한다. 검토를 위해 인덱스를 바꾸지 않는다. 시작 상태와 비교해 기존 변경을 구분한다.
   - SPEC·브리프에 근거 없는 추가물을 찾는다: 요구 없는 옵션·설정·환경변수, 구현이 하나뿐인 추상화, 재시도·캐시·락·큐, 로깅 프레임워크, "나중을 위한" 파라미터, 새 패키지. 자르지 않는 것: 신뢰 경계 입력 검증, 데이터 유실을 막는 에러 처리, 보안, 접근성, 명시된 요구.
   - 후보가 있으면 한 번에 묶어 제거를 제안(추천 표시) → 사람이 고른 것만 제거 → 검증 재실행 → 거절·축소한 AI 제안으로 결정 기록. 없으면 바로 8번.
8. **마무리**:
   - `git status --short --untracked-files=all`을 시작 상태와 비교한다(병렬이면 범위를 합쳐서). 범위 밖 변경은 보존하고, 새로 생긴 변경의 출처가 불명확하면 경로를 보고한다. 임의로 되돌리지 않는다.
   - 실제 구현·테스트를 근거로 [../interview/learning.md](../interview/learning.md)의 `docs/KNOWLEDGE.md`에 알고리즘·복잡도·경계 사례를 갱신한다. 바뀐 내용에 의존하는 기존 퀴즈·해설은 함께 정정한다. 작업자 보고만으로 사실을 확정하지 않는다.
   - `docs/TASKS.md` 상태: DONE, 또는 BLOCKED + 사유(계약 변경 요청이면 BLOCKER 표로). 병렬 실행 중 공유 문서 수정은 루트만 한다.
   - DONE이면 [git-workflow.md](git-workflow.md)의 파일별 검토·커밋 절차로 `"<ID>: <슬라이스 한 줄>"` 커밋. 기존 staged 변경은 건드리지 않고 커밋 보류를 명시한다.

## 위임하지 않는 경우
파일 1~2개, 10분 이내의 변경은 루트에서 직접 해도 된다. tmux·Codex가 없거나 실행이 허용되지 않으면 사유를 밝히고 순차 수행한다(같은 브리프·검증·정리·커밋 규칙 적용).

## BLOCKER가 올라왔을 때 (계약 변경)
하위에서 고치게 하지 않는다. 루트에서 ① SPEC 8절(또는 `CONTRACT.md`)과 `fixtures/` 갱신 → ② 결정 기록(CONTRACT가 있으면 변경 이력에도) → ③ 영향받는 슬라이스마다 "갱신된 계약의 <절>을 읽고 반영하라"는 짧은 브리프로 재위임.

## 출력 (15줄 이내)
`검증: <명령> → 통과/실패` · `회귀: N개 중 N개 통과` · 제거 제안(있으면 묶어서) · `커밋: <해시> <메시지>` 또는 보류 사유 → `다음: /clear 후 /delegate <다음 ID>`(남은 P0가 없으면 `/wrapup`) → 마지막 두 줄 `추가하지 않은 것:` / `확인하지 못한 것·리스크:`. 검증 실패면 다음 슬라이스로 안내하지 않는다.
