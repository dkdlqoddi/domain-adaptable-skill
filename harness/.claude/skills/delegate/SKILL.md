# /delegate — 슬라이스 하나를 끝까지

사용: `/delegate <슬라이스 ID 또는 한 줄 설명> [--parallel | --serial]` — 기본은 지정 슬라이스 하나, `--parallel`은 독립 TODO를 함께 처리하고 `--serial`은 루트가 직접 수행한다.

## 원칙
루트가 판단하고, 계약과 검증이 명확한 구현만 작은 문맥으로 위임한다. 모델·추론·재시도 선택은 [routing.md](routing.md)를 한 번 읽고 적용한다. 작은 수정·명령 실행은 직접 처리한다.

## 절차
시작 전에 [git-workflow.md](git-workflow.md)의 시작 상태를 확인한다. 기존 변경과 스테이징을 브리프에 남긴다.
1. **대상**: 호출 메시지의 ID를 `docs/TASKS.md`에서 찾는다. 설명만 있으면 새 행을 추가(쓰기 범위·검증 명령 포함)한 뒤 진행.
2. **재료**: 해당 슬라이스 행, SPEC의 해당 기능·공통 제약·비목표·8절, 관련 fixtures·호출부·테스트부터 읽는다. 모듈이 여럿이면 CONTRACT의 관련 절과 `<모듈>/CLAUDE.md`. 도메인은 `docs/domain/README.md`에서 필요한 항목을 고른다. 정확성에 필요한 근거는 추가로 확인한다.
3. **브리프**: [brief.template.md](brief.template.md) 형식으로 `docs/briefs/<ID>.md`에 저장한다. tier·effort와 이유를 한 줄로 적고, 계약 샘플은 **값을 그대로 복사**한다. 전체 문서·대화는 복사하지 않는다.
4. **알리고 확인**: 슬라이스마다 세 줄만 보인다 — `위임: <ID> — <목표>` / `방식: <핵심 처리·알고리즘·자료구조와 이유. 실제 대안이 있으면 한 줄>` / 쓰기 범위·검증 명령·브리프 경로. **마일스톤**(S0, 각 P0의 첫 슬라이스, 알고리즘·자료구조에 실제 대안이 있는 슬라이스)이면 마지막 줄에 "이 방식으로 갈까요? 바꿀 점이 있으면 알려 주세요(없으면 '진행')."를 붙여 답을 기다린다. 병렬이면 묶어서 한 번 묻는다. 답은 브리프와 TASKS 행에 반영하고, 사람이 고르거나 바꾼 방식은 결정으로 기록한다. 그 외 슬라이스는 묻지 않고 5번으로 간다. 검증 명령·쓰기 범위가 비었거나, 병렬 범위가 겹치거나, 기존 변경과 작업 귀속이 불명확할 때만 하나를 더 묻는다(추천안 포함).
5. **실행**: [tmux.md](tmux.md)에 따라 브리프·관련 지침을 전달한다. 기본 `--tier implement`, 복잡하면 `reason`, 정해진 치환·추출만 `light`. 기본 1개, `--parallel`은 의존성이 DONE이고 쓰기·검증 자원이 분리된 2개(최대 6개). 부모는 `wait`로 기다리고 막힌 작업만 `status --tail`로 본다. **모든 보고 회수·작업자 정지 뒤** 6~8번을 처리한다. tmux·CLI 실행 불가 시 Agent 도구(general-purpose)에 같은 브리프와 선택한 모델·effort를 지정한다. 그것도 없거나 `--serial`이면 루트가 직접 구현한다. 같은 실패를 반복 위임하지 않고 routing의 한 번 승급 규칙을 따른다.
6. **검증** (루트에서 직접):
   - P0 수용 조건과 실제 사용자 흐름·오류 처리를 대조한다. 작업자가 고른 테스트만으로 DONE 판정하지 않는다. 누락된 경계·실패 사례는 관련 테스트로 확인한다.
   - 작업자 보고를 받은 경우 루트가 해당 검증을 직접 확인한다. 직접 수행한 검증은 변경 없이 반복하지 않는다. 영향받은 DONE 슬라이스의 회귀를 포함하고, 병렬 묶음의 같은 명령은 통합 후 한 번만 실행한다. 전체 회귀는 통합 체크포인트·`/wrapup`에서 실행하며 TASKS에 시각·결과를 남긴다.
   - 실패하면 재현 먼저: 최소 재현 명령 → 원인·수정 파일·검증 방법 3줄 → 쓰기 범위 안에서 최소 수정(크면 실패 내용을 붙여 재위임) → 다시 실행.
   - 화면이 있는 슬라이스면 빌드 에러를 확인하고, 사람에게 첫 화면·핵심 흐름·빈 상태를 직접 봐 달라고 한 줄로 요청한다.
7. **정리** (과잉 설계):
   - `git diff -- <이번 슬라이스의 변경 파일들>`과 새 파일 내용을 검토한다. 검토를 위해 인덱스를 바꾸지 않는다. 시작 상태와 비교해 기존 변경을 구분한다.
   - SPEC·브리프에 근거 없는 추가물을 찾는다: 요구 없는 옵션·설정·환경변수, 구현이 하나뿐인 추상화, 재시도·캐시·락·큐, 로깅 프레임워크, "나중을 위한" 파라미터, 새 패키지. 자르지 않는 것: 신뢰 경계 입력 검증, 데이터 유실을 막는 에러 처리, 보안, 접근성, 명시된 요구.
   - 후보가 있으면 한 번에 묶어 제거를 제안(추천 표시) → 사람이 고른 것만 제거 → 검증 재실행 → 거절·축소한 AI 제안으로 결정 기록. 없으면 바로 8번.
8. **마무리**:
   - `git status --short --untracked-files=all`을 시작 상태와 비교한다(병렬이면 범위를 합쳐서). 범위 밖 변경은 보존하고, 새로 생긴 변경의 출처가 불명확하면 경로를 보고한다. 임의로 되돌리지 않는다.
   - 학습 문서(KNOWLEDGE·QUIZ)는 여기서 갱신하지 않는다. 마무리 때 실제 코드로 한 번에 정리한다.
   - `docs/TASKS.md` 상태: DONE, 또는 BLOCKED + 사유. 작업자를 썼으면 실행기의 `usage --id <ID>`로 재시도 포함 관측 토큰·미측정 실행 수도 한 줄 기록한다. 공유 문서는 루트만 수정한다.
   - DONE이면 [git-workflow.md](git-workflow.md)의 파일별 검토·커밋 절차로 `"<ID>: <슬라이스 한 줄>"` 커밋. 기존 staged 변경은 건드리지 않고 커밋 보류를 명시한다.
   - 이 슬라이스로 P0 하나가 완성되면 출력에 `마일스톤: <P0> 완료 — <실제로 되는 것 한 줄>`을 넣고 의견을 청한다. 의견은 다음 브리프에, 요구 변경은 `/spec`에 반영한다.

## 위임하지 않는 경우
파일 1~2개의 작은 변경과 테스트·검색·집계만 필요한 작업은 루트에서 직접 처리한다. 실행할 수 있는 작업자가 없으면 사유를 밝히고 같은 브리프·검증·정리·커밋 규칙으로 순차 수행한다.

## BLOCKER가 올라왔을 때 (계약 변경)
하위에서 고치게 하지 않는다. 루트에서 ① SPEC 8절(또는 `CONTRACT.md`)과 `fixtures/` 갱신 → ② 결정 기록(CONTRACT가 있으면 변경 이력에도) → ③ 영향받는 슬라이스마다 "갱신된 계약의 <절>을 읽고 반영하라"는 짧은 브리프로 재위임.

## 출력 (15줄 이내)
`검증: <명령> → 통과/실패` · `방식: <실제 구현된 알고리즘·자료구조 한 줄>` · `회귀: N개 중 N개 통과` · 제거 제안(있으면 묶어서) · `커밋: <해시> <메시지>` 또는 보류 사유 · P0가 끝났으면 `마일스톤:` 줄 → `다음: /clear 후 /delegate <다음 ID>`(남은 P0가 없으면 `/wrapup`) → 마지막 두 줄 `추가하지 않은 것:` / `확인하지 못한 것·리스크:`. 검증 실패면 다음 슬라이스로 안내하지 않는다.
