# /spec — 계약 먼저, 그다음 작업판

## 왜
합칠 때 터지는 이유는 하나다: 인터페이스가 안 맞아서. 입출력을 샘플 값으로 먼저 고정하면 이후 구현은 블록처럼 맞물린다.
"만들지 않을 것"을 문서로 못 박아야 AI가 끼워 넣는 과잉 설계를 근거를 들어 쳐낼 수 있다.
슬라이스마다 검증 명령이 있어야 위임한 결과를 확인할 수 있다.

## 읽기
`docs/SPEC.md`, `docs/domain/README.md`와 인덱스가 가리키는 파일, `docs/GLOSSARY.md`.
코드는 열지 않는다. 기존 코드가 있으면 `find . -maxdepth 2 -type d -not -path '*/node_modules*' -not -path '*/.git*'`와 설정 파일(package.json, pyproject.toml 등) 하나만.
다시 실행할 때(새 요구)는 바뀐 부분만 반영하고, 이미 DONE인 슬라이스는 건드리지 않고 새 슬라이스를 추가한다.

## 1. SPEC 확정
1. 기능 후보마다 근거(domain 파일·인터뷰 회차)를 단다. 근거 없는 기능은 P2 또는 비목표.
2. **P0는 3개 이하.** P0 = 없으면 제출 불가. 각 P0에 검증 가능한 완료 기준 한 줄(명령이나 화면으로 확인 가능하게).
3. 비목표를 반드시 채운다. 인증·권한·캐시·재시도·다국어·확장성·동시 쓰기 같은 "있으면 좋은 것" 중 이번에 안 하는 것을 이름 붙여 적는다.
4. 결정이 필요한 지점은 한 번에 하나씩, 추천안과 이유를 붙여 묻는다. 유추 가능한 것은 유추하고 `(가정)` 표시. 정한 것은 결정으로 기록한다.
5. 용어는 `GLOSSARY.md`의 것을 쓴다. 새 용어가 필요하면 먼저 GLOSSARY에 한 줄 추가.

## 2. 모듈과 계약
1. 모듈은 기본 1개. 나누는 이유는 둘뿐: 검증 방법이 다르다, 병렬로 만들 가치가 있다. 4개를 넘기지 않는다.
2. **모듈이 1개면** `docs/SPEC.md` 8절(입출력 샘플)에 실행 명령, 입력, 기대 출력, 에러 경로 하나를 **구체적인 값**으로 적고, 같은 샘플을 `fixtures/`에 파일로 둔다.
3. **모듈이 2개 이상이면** [contract.template.md](contract.template.md)로 `docs/CONTRACT.md`를 만들어 모듈 사이에 오가는 것을 샘플 값으로 적는다(형식 예시: [contract-examples.md](contract-examples.md)). 모듈마다 `<모듈>/CLAUDE.md`를 [module-claude.template.md](module-claude.template.md)로 만든다(40줄 이하). 폴더 이름은 GLOSSARY 용어로.

## 3. 슬라이스 (`docs/TASKS.md`)
- **S0 = 걸어다니는 뼈대.** 실행되고 입력 하나가 끝까지 지나가 출력까지 간다(내용은 하드코딩이어도 됨). 항상 첫 번째.
- P0 기능 하나당 슬라이스 1~2개. 각 행에 쓰기 범위 폴더와 검증 명령을 **반드시** 적는다. 검증 명령은 가장 싼 것: 테스트 1개, curl 1줄, 픽스처 입력→출력 diff.
- P1은 TODO로 뒤에. P2는 적지 않는다. 표의 한 칸은 2문장 이하.
- 끝내기 전 확인: 쓰기 범위가 서로 겹치지 않는다. 모든 검증 명령이 실행은 된다(미구현이라 실패하는 것은 괜찮다).

## 4. 커밋
`git add docs/ fixtures/` (모듈 CLAUDE.md를 만들었으면 그것도) → `git commit -m "spec: <P0 요약 한 줄>"`.

## 출력 (15줄 이내)
P0 목록(ID와 기능만 한 줄씩. 완료 기준은 SPEC에 있으니 화면에 쓰지 않는다) → `비목표: ...` 한 줄 → 슬라이스 목록(ID·한 줄씩) → `가정 N개(SPEC 5·7절)` 한 줄 → 마지막 줄: "다음: `/delegate S0`"(다시 실행했으면 새 슬라이스).
