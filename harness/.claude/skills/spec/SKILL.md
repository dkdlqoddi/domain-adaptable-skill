# /spec — 계약 먼저 (Contract-First)

## 왜
병렬로 만든 것이 터지는 이유는 하나다: 합칠 때 인터페이스가 안 맞아서.
계약을 먼저 고정하면 이후 구현은 블록처럼 맞물린다.
또한 "만들지 않을 것"을 문서로 못 박아야 AI가 끼워 넣는 과잉 설계를 근거를 들어 쳐낼 수 있다.

## 읽기
`docs/SPEC.md`, `docs/domain/README.md`와 인덱스가 가리키는 파일, `docs/GLOSSARY.md`.
코드는 열지 않는다. 기존 코드가 있으면 `ls` 2단계와 설정 파일(package.json, pyproject.toml 등) 하나만.

## SPEC.md 확정 (`spec` 또는 `all`)
1. 기능 후보마다 근거(domain 파일·인터뷰 회차)를 단다. 근거 없는 기능은 P2 또는 비목표.
2. **P0는 3개 이하.** P0 = 없으면 제출 불가. 각 P0에 검증 가능한 완료 기준 한 줄(명령이나 화면으로 확인 가능하게).
3. 비목표를 반드시 채운다. 인증·권한·캐시·재시도·다국어·확장성·동시 쓰기 같은 "있으면 좋은 것" 중 이번에 안 하는 것을 이름 붙여 적는다.
4. 결정이 필요한 지점은 한 번에 하나씩, 추천안과 이유를 붙여 묻는다. 유추 가능한 것은 유추하고 `(가정)` 표시.
5. 용어는 `GLOSSARY.md`의 것을 쓴다. 새 용어가 필요하면 먼저 GLOSSARY에 한 줄 추가.

## CONTRACT.md 확정 (`contract` 또는 `all`)
1. 모듈 수는 최소로. 나누는 이유는 둘뿐: 검증 방법이 다르다, 병렬로 만들 가치가 있다. 작은 과제는 모듈 1~2개가 정상이다.
2. 모듈 사이에 오가는 것을 **구체적인 샘플 값**으로 적는다(스키마만 적지 말고 샘플 JSON·파일·명령 1개씩). 샘플은 `fixtures/`에 파일로 저장한다. 모듈은 서로의 코드가 아니라 이 샘플을 보고 개발한다.
3. 형식은 도메인에 맞게 고른다: HTTP API / CLI / 파일 포맷 / 함수 시그니처 / 상태 전이. 안 쓰는 섹션은 지운다. 예시: [contract-examples.md](contract-examples.md)
4. 에러·실패 경로도 샘플 하나씩(잘못된 입력 → 어떤 응답·종료코드).

## 출력
파일별 변경 요약 한 줄씩 → **아직 가정인 항목** 목록(다음 인터뷰 질문 후보) → 마지막 줄: "다음: `/workspace`".
